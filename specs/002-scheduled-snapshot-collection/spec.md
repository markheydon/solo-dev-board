# Feature Specification: Scheduled snapshot collection

**Feature Branch**: `002-scheduled-snapshot-collection`

**Created**: 2026-11-23

**Status**: In progress (Phases 1–11 implemented on branch; Phase 12 closes 2026-11-24 spec revision)

**Input**: User description: "Follow-on to the operator snapshot collection. In hosted sign-in, run that same collection unattended on a schedule so the operator does not have to request it and does not have to wait on screen while a longer collection runs. The first delivery plan fills the scheduled scan queue once per UTC day at 05:00 UTC. Queued work is processed whenever the scheduled collection process is running, at any time of day or night. The lean local posture does not get a schedule. Starting a collection by hand remains."

## Clarifications

### Session 2026-11-24

- Q: Does wall-clock time restrict when queued scheduled collections run? → A: No. Once an operator is on the scheduled scan queue, processing proceeds whenever the scheduled collection process is running, at any time of day or night. Clock-time rules apply only to when the queue is filled for a scheduled occasion, not to draining entries already on the queue.
- Q: What does 05:00 UTC mean in this feature? → A: It is the initial planned time to fill the queue once per UTC calendar day, together with the existing grace window for whether that fill happens. It is not a limit on when queued work may run or finish. Changing fill frequency (for example every ten minutes) or offering per-operator schedules may arrive in a later feature; this specification must not forbid that.
- Q: When are eligibility rules (admission, 30 days, stored access, and the rest) evaluated for placing someone on the scheduled scan queue? → A: When the queue is filled for that occasion and when the product states the next occasion on the Repositories page. Those rules prevent someone from being placed on the queue when they fail. Clock time does not, on its own, remove an entry already on the queue.
- Q: Are the rules for placing a scan on the queue the same as the rules for running a scan that is already queued? → A: No. Queuing follows the planned schedule (initial default once per UTC day at 05:00 UTC, with the grace window). Running a queued scan is not limited by time of day: anything already on the queue is processed whenever the scheduled collection process is running. A queued scan still does not run when that account is not allowed to use the product, or when that user's latest completed hosted sign-in is outside the last 30 days. Those checks belong to running a queued scan, not to the 05:00 fill clock. Queuing and running are different processes and may use different rules.
- Q: When a queued scan is reached and that person is no longer allowed to use the product, or their latest sign-in is now older than 30 days, what should happen to that queue entry? → A: Do not run it. Remove the queue entry. Do not record a failed collection. Continue with the next person. The Repositories page states that no scheduled collection will run, and why. Any earlier successful snapshot stays unchanged. The page does not keep showing that run as in progress, failed, or interrupted.
- Q: After a rate-limit or unexpected-error failure on a scheduled collection, must a further try wait in wall-clock time as well as going to the back of the queue (for example when this account is alone in the queue)? → A: Yes. Each further try still goes to the back of the queue. Before that further try may start, a minimum wait applies. For a GitHub rate-limit failure, the product waits at least the GitHub-indicated retry period when it already has one from that failure, otherwise at least 2 minutes. For an unexpected error, staggered minimum waits apply (3, 6, then 12 minutes; see later clarification). Other accounts still queued ahead run first. When no other account is ahead, the further try must not start until that minimum wait has elapsed.
- Q: What fixed minimum wall-clock delay should scheduled further tries use when a rate-limit failure does not include a usable GitHub retry period, and for every unexpected-error further try? → A: 2 minutes for rate-limit failures without a GitHub-indicated retry period only (see stagger rule below for unexpected errors).
- Q: For scheduled further tries after an unexpected error (not a GitHub rate limit and not a failure that already supplies a known retry time), what minimum wait should apply before each further try may start? → A: Staggered minimum waits measured from that failed attempt: 3 minutes before the first further try, 6 minutes before the second further try, 12 minutes before the third further try. Each further try still goes to the back of the queue.

### Session 2026-11-23

- Q: When someone is not signed in at 05:00 UTC, how should the product decide that they still belong to a listed organisation? → A: Use the organisation logins saved from their last completed sign-in, together with the allow lists as they stand at 05:00 UTC. Do not ask GitHub again only to check membership.
- Q: When several people are eligible at the same scheduled fill, does each collection start then, or may the product start them one after another? → A: Place them on the queue when that occasion is filled (initial default 05:00 UTC). Run one scheduled collection at a time when the queue is processed, which may be at any time the scheduled collection process is running. A rate-limit or unexpected-error retry goes to the back of that queue so it does not hold up other accounts.
- Q: If the scheduled collection process is not running at 05:00:00 UTC but is running again a few minutes later, is that day's queue filled? → A: Fill the queue if the scheduled collection process is running again within 15 minutes after 05:00:00 UTC. After that, the day is missed.
- Q: If more than one copy of the scheduled collection process is running at the daily occasion, how many times is each eligible person queued and collected? → A: Each eligible person is queued once and collected once for that occasion, even when more than one copy of the scheduled collection process is running.
- Q: If today's collection is queued for someone but has not started, can they still start that collection themselves? → A: No. While they are queued, or a collection is in progress, the start control does not start one. They wait for the queue.
- Q: If the scheduled collection process stops while someone is still on today's queue, including waiting at the back for another try, what should happen to that queued work when the scheduled collection process is running again? → A: Queued work is still taken after the scheduled collection process is back, including a further try waiting at the back. It runs only when that person is still allowed and still inside the 30-day window. A collection that was in progress when the scheduled collection process stopped is interrupted and does not rejoin the queue.
- Q: While a daily collection is waiting at the back of the queue for another try, what should the Repositories page show for that run? → A: Show the same daily run as in progress until it succeeds, fails, or is interrupted, including while it waits at the back. Do not list the tries.
- Q: For the day's collection to be queued and to finish, does the operator-facing app have to be running, or can that work happen while the app is not running? → A: The day's collection is queued and can finish while the operator-facing app is not running. A scheduled collection process, separate from the operator-facing app, does that work. If that process is down from 05:00:00 UTC through 05:15:00 UTC, the day is still missed. The spec records this split and does not name the host, project, or wiring.

## User Scenarios & Testing *(mandatory)*

**Scheduling model (all stories below):** In hosted sign-in, eligible operators are placed on a **scheduled scan queue** at each **scheduled occasion** (a queue fill). The **initial delivery default** is one occasion per UTC calendar day, nominally at 05:00 UTC, with the grace and miss rules described for whether that fill happens. **Queue processing** is a different process: entries on that queue, including retries at the back, are taken whenever the scheduled collection process is running, without regard to time of day or night. A collection does not have to start or finish in the same hour as the fill. When the queue reaches an entry, that scan does not run if the person is not currently allowed to use the product, or if their latest completed hosted sign-in is then older than 30 days. The product removes that queue entry, records no failed collection, and continues with the next person. The Repositories page states that no scheduled collection will run, and why. Those are run rules, not the fill clock. Scenarios below name 05:00 UTC where they exercise that default fill; they are not claiming that processing is limited to that hour.

### User Story 1 - Collect overnight without the operator waiting (Priority: P1)

In hosted sign-in, the collection the operator can already start by hand is also placed on the scheduled scan queue at each scheduled occasion. The initial plan fills that queue once per UTC day at 05:00 UTC. One scheduled collection runs at a time across the queue. A person's collection runs when the queue reaches them, as soon as the scheduled collection process can take the next entry, which may be any time after they were queued, provided they are still allowed to use the product and their latest completed hosted sign-in is still no older than 30 days at that moment. If either of those is no longer true, that queued scan does not run. The product removes that queue entry, records no failed collection, and continues with the next person. The Repositories page states that no scheduled collection will run, and why. Any earlier successful snapshot stays unchanged. Passing the fill clock is not what decides that. It does not have to be in progress at the fill instant. The queue includes each person who, at fill time for that occasion, has completed a hosted sign-in at least once in the last 30 days, is currently allowed to use the product, and is not waiting because a scheduled collection failed when the stored access could not be used. Being allowed is not enough on its own. A person who is allowed but has never completed a hosted sign-in is not included, so a long allow list is not scanned in full. A person who completed sign-in inside that window but is no longer allowed at fill time is not included. When hosted admission is on, a person is allowed when their user login is listed or an organisation login saved from their last completed sign-in is on the organisation list as it stands when the queue is filled for that occasion. The product does not ask GitHub again only to check membership. When hosted admission is off, the lists do not refuse anyone, and the set is still only people who signed in inside the window and are not waiting after invalid stored access. The person does not need to be signed in, on the Repositories page, or watching the screen. The operator-facing app does not have to be running. A scheduled collection process, separate from that app, fills the queue at each occasion and processes it. This specification does not name the host, project, or wiring of that process. A long collection can finish while they are away, including hours after the fill. When the run succeeds, it is the same snapshot a collection they started themselves would have produced: one current snapshot of the repositories linked to their personal account, public and private, with the same facts the operator snapshot collection already records. It replaces the previous successful snapshot. It is not a second scanner and not a second snapshot.

**Why this priority**: Later checks inside this collection are expected to take longer. A collection that starts only when the operator asks, and that they feel they must watch, becomes poor use of the product. The overnight start does the work when they are not waiting for it.

**Independent Test**: Have two people complete hosted sign-in, each with a known personal catalogue, each inside the last 30 days, and each currently allowed. Leave both signed out and do not open the Repositories page. When the scheduled fill passes (initial default 05:00 UTC) and the scheduled collection process is available, with the operator-facing app not running, confirm both are queued and each collection runs, one at a time, when the queue is processed (which may be hours after fill). Confirm a third person who completed sign-in inside the window but is no longer allowed at fill time receives none. After each successful run, confirm the kept snapshot matches the catalogue a hand-started collection would have kept for that same person, and that neither sees the other's result. Separately, confirm a person whose latest sign-in is older than 30 days, and a person who is allowed but has never signed in, receive no unattended collection.

**Acceptance Scenarios**:

1. **Given** hosted sign-in, a person whose latest completed sign-in is no older than 30 days, who is currently allowed to use the product, who is not waiting after invalid stored access, and the scheduled collection process is running at 05:00:00 UTC, **When** 05:00:00 UTC passes and nobody opens the Repositories page or chooses the start control, **Then** that person is placed on that occasion's queue at fill time. Their collection runs when the queue reaches them, whenever the scheduled collection process next takes that entry, which may be at any time of day, provided they are still allowed and their latest completed sign-in is still inside 30 days. If either check then fails, that queued scan does not run: the queue entry is removed, no failed collection is recorded, and the next queued person is taken.
2. **Given** that daily collection succeeds, **When** the operator later opens the Repositories page, **Then** the page shows success, when that collection finished, and how many repository entries the snapshot holds. The snapshot is the one a hand-started collection would have kept for that operator. The page does not list the entries.
3. **Given** a successful snapshot already exists, **When** a later daily collection succeeds, **Then** the kept snapshot is that new collection. Older runs are not listed.
4. **Given** the operator is not signed in, is not using the product, and the operator-facing app is not running, **When** the daily collection is due and the scheduled collection process is running, **Then** the collection still starts and can finish.
5. **Given** person A and person B have each completed a hosted sign-in no older than 30 days, **When** the daily occasion passes, **Then** each is queued and each receives their own collection and their own snapshot. Only one of those daily collections is in progress at a time. B does not see A's entries, finish time, or collection status.
6. **Given** the operator opens the Repositories page at a time that is not the daily occasion and does not choose the start control, **When** the page is shown, **Then** no collection starts because of that visit.
7. **Given** a person whose latest completed sign-in is older than 30 days at 05:00 UTC, **When** the daily occasion passes, **Then** no unattended collection starts for them, including when hosted admission would let them in.
8. **Given** a person who has never completed a hosted sign-in, **When** 05:00 UTC passes, **Then** no unattended collection starts for them, including when their login is listed for admission.
9. **Given** a person whose latest completed sign-in was exactly 30 days before 05:00 UTC, **When** the daily occasion passes, **Then** a collection starts for them.
10. **Given** a successful daily collection, **When** more than 30 days pass from the latest completed sign-in and the person does not sign in again, **Then** the next daily occasion does not start a collection. Earlier successful collections do not keep the window open.
11. **Given** a person completed a hosted sign-in inside the last 30 days, and hosted admission is on with that person on neither the user list nor an organisation list, **When** 05:00 UTC passes, **Then** no daily collection starts for them.
12. **Given** hosted admission is on and both the user list and the organisation list are empty, **When** 05:00 UTC passes, **Then** no daily collection starts, including for people whose latest completed sign-in is no older than 30 days.
13. **Given** hosted admission is off, **When** 05:00 UTC passes, **Then** a collection starts only for people whose latest completed sign-in is no older than 30 days and who are not waiting after invalid stored access. Turning admission off does not add anyone who has not signed in.
14. **Given** a person was allowed by their user login, completed sign-in inside the last 30 days, and is then removed from that list, **When** the next 05:00 UTC passes, **Then** no daily collection starts for them.
15. **Given** a person was allowed only because an organisation login saved from their last completed sign-in is on the organisation list, they completed sign-in inside the last 30 days, and that organisation is then removed from the list, **When** the next 05:00 UTC passes, **Then** no daily collection starts for them.
16. **Given** a person remains on the user list after the organisation list no longer includes an organisation login saved from their last completed sign-in, their latest completed sign-in is no older than 30 days, and they are not waiting after invalid stored access, **When** 05:00 UTC passes, **Then** a daily collection still starts for them.
17. **Given** a person was removed from admission and is allowed again before the next 05:00 UTC, their latest completed sign-in is still no older than 30 days, and they are not waiting after invalid stored access, **When** that occasion passes, **Then** a daily collection starts for them.
18. **Given** many people are allowed and only some of them have ever completed a hosted sign-in, **When** 05:00 UTC passes, **Then** a collection starts only for those who completed sign-in inside the last 30 days, are still allowed, and are not waiting after invalid stored access.
19. **Given** two copies of the scheduled collection process are running and two people are eligible, **When** the daily occasion passes, **Then** each person is queued once and collected once. Their runs do not overlap.
20. **Given** the operator-facing app is not running and the scheduled collection process is running at 05:00:00 UTC, **When** 05:00:00 UTC passes for an eligible person, **Then** that person is queued and the collection can finish.
21. **Given** a person was placed on the queue at the daily fill while allowed and inside 30 days, **When** the queue reaches them after they are no longer allowed to use the product, or after their latest completed sign-in is older than 30 days, **Then** that queued scan does not run. The queue entry is removed, no failed collection is recorded, and the next queued person is taken. The page states that no scheduled collection will run, and why, and it does not show that run as in progress, failed, or interrupted. Any earlier successful snapshot stays unchanged. They are no longer queued, so the start control can start a collection when they can use the product. The time of day is not the reason. A person who is still allowed and still inside 30 days is not skipped because the clock has moved on from 05:00 UTC.

### User Story 2 - Keep starting a collection by hand (Priority: P1)

The daily collection does not remove the control the operator already uses. In hosted sign-in they can still start a collection from the Repositories page, including after a daily collection has failed, except while they are queued for the current occasion or a collection for them is in progress. While they are queued, including before that collection has started, the start control does not start one. They wait for the queue. That is the same hand-started collection they already have. This feature does not add another way to ask for a retry. A success they start themselves replaces the kept snapshot in the same way a daily success does, including a snapshot that the overnight run produced earlier that day.

**Why this priority**: The operator still needs a collection when they want a fresh snapshot before the next overnight run. The schedule is an extra way the same collection starts, not a replacement for asking.

**Independent Test**: After a successful daily collection, start a collection from the Repositories page and confirm the new success replaces the overnight snapshot. Also start a collection by hand on a day when the daily run has not happened yet, and confirm that run can succeed on its own.

**Acceptance Scenarios**:

1. **Given** hosted sign-in, and the operator is not queued for the current occasion and no collection for them is in progress, **When** the operator looks on the Repositories page, **Then** they can still start a collection themselves.
2. **Given** the operator is waiting in today's queue and the collection has not started, **When** they choose the start control, **Then** a collection does not start from that control. They remain queued.
3. **Given** a successful daily snapshot, **When** the operator starts a collection and it succeeds, **Then** the kept snapshot is that newer collection and the page shows the new finish time.
4. **Given** the operator starts a collection themselves, **When** they read the current run, **Then** the page shows that they started it, and does not describe it as the daily occasion.
5. **Given** a daily collection has failed, **When** the operator looks for a separate retry control, **Then** there is none. The existing start control is how they collect again themselves.

### User Story 3 - Leave the operator's own machine unscheduled (Priority: P1)

In the lean local posture, including a personal deployment that stays in that posture, there is no scheduled collection process, and nothing collects because the clock reached 05:00 UTC. The product still explains that nothing collects on a schedule, and that the snapshot is kept on this machine rather than promised on another machine. The operator can still collect when they ask, without being asked to add anything before they can do that.

**Why this priority**: The overnight run depends on the hosted sign-in posture. Operators on their own machine keep the collection they already have, and the product tells them the truth about the missing schedule instead of blocking the collection.

**Independent Test**: In the lean local posture, leave the operator-facing app running across 05:00 UTC without choosing the start control, and confirm no collection starts. Read the explanation. Then start a collection by hand and complete it.

**Acceptance Scenarios**:

1. **Given** the lean local posture, **When** 05:00 UTC passes and the operator does not choose the start control, **Then** no collection starts.
2. **Given** the lean local posture, **When** the operator views collection on the Repositories page, **Then** the product explains that nothing collects on a schedule and that the snapshot is kept on this machine rather than promised on another machine.
3. **Given** the lean local posture, **When** the operator starts a collection, **Then** they can complete it when they ask, without being asked to add infrastructure.
4. **Given** the lean local posture and a collection the operator started, **When** they read the current run, **Then** the page does not describe a daily occasion.

### User Story 4 - Run one collection at a time (Priority: P1)

A daily occasion never starts a second collection for an operator who already has one in progress or already waiting on that day's queue. Only one daily collection runs at a time. Other queued people wait and are not a missed day. Choosing the start control never starts a second collection while that operator is queued for the current occasion or the daily run is in progress, including while a retry waits at the back of the queue. The operator can keep using the rest of the product while that run continues. If they are on the Repositories page, the state, times, and recorded count update without them leaving or reloading. The page says whether the current run was started by them or by the daily occasion.

**Why this priority**: Two collections at once for the same operator would make the count and the kept snapshot ambiguous. The operator needs to see movement, and needs to know why a run is going when they did not choose it.

**Independent Test**: Start a collection by hand so that it is still in progress at 05:00 UTC, and confirm a second run does not start. Separately, queue two eligible people, confirm only one daily collection is in progress at a time, and confirm the second starts as soon as possible after the first finishes. Be on the Repositories page when the daily run starts, confirm the page shows that the daily occasion started it and that the recorded count rises without a reload, and confirm the start control does not start another run.

**Acceptance Scenarios**:

1. **Given** a collection for that operator is already in progress at 05:00 UTC, or they are already waiting on the previous occasion's queue, **When** the daily occasion passes, **Then** a second collection is not queued, and the current run or queue entry remains the one already there.
2. **Given** a daily collection is in progress, or the operator is waiting in today's queue before it has started, **When** the operator chooses the start control, **Then** a second collection does not start.
3. **Given** a daily collection is in progress, **When** the operator views the Repositories page, **Then** they see that it is in progress, that the daily occasion started it, when it started, and how many repositories have been recorded so far.
4. **Given** a daily collection covering more than one repository is still running, **When** the operator stays on the Repositories page, **Then** the recorded count becomes higher than on the earlier look without them leaving or reloading.
5. **Given** a daily collection is in progress, **When** the operator leaves the Repositories page and uses another part of the product, **Then** that other part remains usable without waiting for the collection to finish.
6. **Given** the daily occasion finds a collection already in progress and does not start another, **When** the operator looks for a record of that skipped occasion, **Then** there is no separate skipped entry. The page shows the current run, the latest successful snapshot if one exists, and the following day's 05:00 UTC when that occasion will still start a collection for them.

### User Story 5 - See when the next scheduled queue fill is (Priority: P2)

On the Repositories page in hosted sign-in, the operator sees when the product will next try to queue them for a scheduled collection, and whether that will actually include them. For the initial delivery default, that next fill is named as 05:00 UTC for every operator, not 05:00 in their own zone. That label describes the planned queue fill, not the hour when their collection must run or finish. When the next such fill will queue a collection for them, the page names that occasion as 05:00 UTC. A run that starts later because the queue has not reached them yet, including in a different hour or on a later UTC day, is still part of that same scheduled occasion unless a later feature changes how occasions work. When no fill will queue them, the page says that no scheduled collection will run, and why, and it does not imply that one will still happen that night or at the next 05:00 UTC fill. That statement is shown even when no collection has ever run, whether by hand or on the schedule. The page still shows when the last successful collection finished, whether that success was started by the operator or by the scheduled occasion, as the operator snapshot collection already does. A scheduled run that failed because the stored access could not be used is shown as that failure. The page does not then say that another collection will run tonight. They can still start a collection themselves when they can use the product. They cannot change the fill time, how often the queue is filled, or the 30 days in this feature. This feature does not add a place to edit any of those.

**Why this priority**: A standing sentence that a collection runs each day is wrong on the morning after stored access could not be used, and it is wrong when this operator will not be included. The operator needs the real next queue fill, or a clear statement that there is not one, including before any collection has ever run. An operator in another zone can misread 05:00 as their local morning. Choosing a different fill time, frequency, or per-operator schedule is a later decision; this story only states what the product will show for the current default.

**Independent Test**: In hosted sign-in, open the Repositories page before any collection has run and confirm it names the next 05:00 UTC that will start one, or says that none will run. After a successful hand-started or daily collection, confirm that finish time is still shown and the next real occasion is named as 05:00 UTC. Cause last night's daily collection to fail because the stored access could not be used, and confirm the page states that failure and does not imply that another collection will run tonight. Confirm there is no control that changes the time, how often, or the 30 days.

**Acceptance Scenarios**:

1. **Given** hosted sign-in, no collection has ever run, and the next 05:00 UTC will start a collection for that operator, **When** they view collection on the Repositories page, **Then** the page names that occasion as 05:00 UTC, does not pretend a collection has already happened, and shows that they can still start a collection themselves.
2. **Given** a successful collection exists, whether the operator started it or the daily occasion did, and a later 05:00 UTC will start a collection for them, **When** they view the page, **Then** the page shows when that success finished and names the next occasion as 05:00 UTC.
3. **Given** the latest daily collection failed because the stored access could not be used, **When** the operator views the page, **Then** the page shows that failure and the sign-in or token reason, shows the finish time of the latest successful collection when one exists, and states that no scheduled collection will run until they sign in again. It does not state that a collection will run tonight or at the next 05:00 UTC.
4. **Given** the operator's latest completed sign-in is older than 30 days, or the next 05:00 UTC would fall outside that window, **When** they view the page, **Then** the page states that no scheduled collection will run until they sign in again. It does not name a 05:00 UTC occasion as if one will start.
5. **Given** the operator can view the Repositories page and is no longer allowed to use the product, **When** they view collection on that page, **Then** the page states that no scheduled collection will run because they are not allowed. It does not imply that a collection will run tonight or at the next 05:00 UTC.
6. **Given** the latest daily collection failed for a GitHub rate limit or an unexpected error, or was interrupted, and a later 05:00 UTC will still start a collection for that operator, **When** they view the page, **Then** the page shows that outcome and still names that next occasion as 05:00 UTC.
7. **Given** today's 05:00 UTC has not yet passed and the operator is eligible for it, **When** they view the page, **Then** the named occasion is today at 05:00 UTC.
8. **Given** today's occasion was missed because the scheduled collection process was not running at any time from 05:00:00 UTC through 05:15:00 UTC, or it did not queue this operator because a collection was already in progress, and the operator will still be eligible at the following 05:00 UTC, **When** they view the page, **Then** the named occasion is the following day at 05:00 UTC, not later today.
9. **Given** the operator is still waiting in today's queue and their collection has not started, **When** they view the page after 05:00 UTC, **Then** the named occasion remains today at 05:00 UTC. The page does not describe the day as missed and does not show the run as in progress until the collection starts.
10. **Given** an operator whose local zone is not UTC, **When** they read the named occasion, **Then** the stated time is 05:00 UTC.
11. **Given** hosted sign-in, **When** the operator looks for a way to change the time, how often the collection runs, or the 30 days, **Then** this feature offers no such control and no separate settings page for it.

### User Story 6 - Keep the last success when the overnight run does not finish cleanly (Priority: P2)

A daily collection that fails uses the same short reasons the operator already understands: a sign-in or token problem, a GitHub rate limit, or an unexpected error. The previous successful snapshot stays as it was, and its finish time stays visible beside the failed run. If the scheduled collection process stops while a pass of a daily collection is running, the next visit shows that run as interrupted, with a short reason that the scheduled collection stopped before it finished. That reason does not say that the operator-facing app stopped. The operator-facing app stopping, or not running, does not interrupt a daily pass and does not miss the day. That pass does not rejoin the queue. People still waiting on today's queue, including a further try waiting at the back, are not interrupted by that stop. That queued work is still taken as soon as possible after the scheduled collection process is back, and it runs only when that person is still allowed and still inside 30 days. The operator can start a collection themselves afterwards, using the start control they already have, once they are not queued and no collection for them is in progress. This feature does not add a retry control.

Access the operator already granted is what the daily collection uses. If that stored access cannot be used, the run fails at once with the sign-in or token reason. It is not tried again as part of that occasion. After that failure, no further daily collection starts until the operator signs in successfully again. That sign-in lifts the wait and restarts the 30-day window from the new sign-in.

A GitHub rate limit or an unexpected error is treated as a problem that may pass quickly. The same daily collection is tried again up to 3 times. Each further try goes to the back of the queue and must not start until a minimum wall-clock wait has elapsed. For a rate-limit failure, that wait is at least the GitHub-indicated retry period when the product already has one from that failure, otherwise at least 2 minutes. For an unexpected error, each further try waits at least a staggered minimum measured from that failed attempt: 3 minutes before the first further try, 6 minutes before the second, 12 minutes before the third. Queue position alone is not enough when this account is alone in the queue. The further try still does not hold the queue up for other accounts: anyone already ahead runs first, and the minimum wait still applies before the further try may start. Those further tries are part of the same run, not a new occasion and not a list of attempts. While a further try waits at the back, the page shows that same run as in progress. It does not show the run as failed, and it does not list the tries. If one of them succeeds, that success is the run and the remaining tries do not happen. If they all fail, the page shows one short reason and when that run failed, together with the finish time of the latest successful snapshot when one exists. That failure does not stop the next eligible day, and it does not move the 30-day window. An interruption is not one of these further tries. It is a pass that was running when the scheduled collection process stopped, and that run is shown as interrupted. The page also shows a further try waiting at the back as in progress, but a stop during that wait is not an interruption. An interruption does not rejoin the queue. A further try already waiting at the back is queued work, not an interruption, and it is still taken after the scheduled collection process is back. It runs only when that person is still allowed and still inside 30 days. An interruption does not stop the next eligible day.

**Why this priority**: An overnight failure must not wipe the snapshot later features already rely on. A brief problem calling GitHub should not be the result the operator sees the next morning. The operator should see the same kind of outcome they see when a collection they started does not finish, and should still see when the last successful collection finished. Repeating a daily collection that the stored access cannot support would keep failing without the operator present.

**Independent Test**: Keep a successful snapshot. Cause a rate limit or an unexpected error on the daily collection and confirm the same run is tried again up to 3 times by going to the back of the queue and waiting the required minimum before each further try. While that further try waits, confirm the page shows the same run as in progress, not as failed, and does not list the tries. With only one eligible account queued, confirm the next try does not start immediately after the failure (and for unexpected errors confirm staggered waits of 3, 6, and 12 minutes between further tries). With another account already queued, confirm that other account runs before the retry and that the minimum wait still applies before the further try starts. Confirm a try that then succeeds becomes the kept snapshot, and confirm that when every try fails the page shows one reason, when the run failed, and the unchanged earlier finish time. Cause a sign-in or token failure and confirm there is no further try that occasion, and that the following 05:00 UTC starts nothing until the operator signs in successfully again. Confirm the next eligible day still starts after a rate limit, an unexpected error, or an interruption. Confirm the page has no retry control, and that the existing start control can still collect. Separately, stop the scheduled collection process during a daily run and confirm the next visit shows the run as interrupted. Stop the scheduled collection process while a further try is only waiting at the back of the queue and confirm that queued work still runs and is not shown as interrupted.

**Acceptance Scenarios**:

1. **Given** a successful snapshot exists, **When** a later daily collection fails, **Then** the page shows when it failed, that the daily occasion started it, and one short reason (a sign-in or token problem, a GitHub rate limit, or an unexpected error), and it still shows the finish time of that successful snapshot. The previous snapshot's entries and finish time are unchanged.
2. **Given** no successful snapshot exists, **When** the first daily collection fails, **Then** there is still no snapshot, and the page shows the short reason and when it failed.
3. **Given** a pass of a daily collection is running, **When** the scheduled collection process stops before that pass finishes and the operator next visits the Repositories page, **Then** the run is shown as interrupted, it is not shown as in progress, it does not rejoin the queue, and any previous successful snapshot is unchanged.
4. **Given** a person is waiting on today's queue before their collection has started, or is waiting at the back for a further try, **When** the scheduled collection process stops and is running again, **Then** that queued work is still taken as soon as possible, and it runs only when that person is still allowed and still inside 30 days. It is not shown as interrupted. A further try that was waiting is still shown as in progress until that run succeeds, fails, or a later pass is interrupted, or until the run rules refuse it. If it is refused because they are not allowed or are outside 30 days, the entry is removed, no failed collection is recorded, and the page stops showing that run as in progress.
5. **Given** the access that operator already granted cannot be used at 05:00 UTC, **When** the daily collection runs, **Then** the run fails with the sign-in or token reason and does not publish a new successful snapshot.
6. **Given** a daily collection has recorded some repositories and then fails or is interrupted, **When** the operator reads the page, **Then** those in-progress recordings are not presented as a new successful snapshot.
7. **Given** a daily collection has failed because the stored access cannot be used, **When** a later 05:00 UTC passes and the operator has not signed in successfully again, **Then** no daily collection starts. The failed run remains what the page shows, including the sign-in or token reason.
8. **Given** that wait, **When** the operator views the Repositories page, **Then** the page shows the failed run, the sign-in or token reason, and that no scheduled collection will run until they sign in again. It does not imply that one will run tonight or at the next 05:00 UTC.
9. **Given** that wait, **When** the operator signs in successfully after 05:00 UTC on that day, **Then** they can start a collection themselves, no unattended collection starts later that same UTC day, and the 30-day window is measured from that new sign-in.
10. **Given** that wait, and the operator has completed a hosted sign-in again and is currently allowed to use the product, **When** the next 05:00 UTC passes, **Then** a daily collection starts. If that sign-in completed but they are not currently allowed, no daily collection starts.
11. **Given** a daily collection fails because of a GitHub rate limit or an unexpected error, or is interrupted, **When** the next 05:00 UTC passes, the latest completed sign-in is still no older than 30 days, and the person is currently allowed, **Then** a daily collection starts. That outcome does not restart the 30-day window. If they are no longer allowed, no daily collection starts.
12. **Given** a daily collection hits a GitHub rate limit or an unexpected error, **When** that attempt fails, **Then** the same run goes to the back of the queue, up to 3 further tries, and each further try waits at least the applicable minimum (GitHub-indicated retry period when the product has one from a rate-limit failure, otherwise 2 minutes; unexpected-error failures use staggered minimums of 3, 6, then 12 minutes before the first, second, and third further tries). Other accounts already queued run before that further try. The page shows that same run as in progress while the further try waits. It does not list those tries separately, and it does not show the run as failed.
13. **Given** one account is waiting at the back of the queue for a further try and another eligible account is queued, **When** the next daily collection can run, **Then** the other account's collection starts first. The waiting retry does not hold that other account up, and the minimum wait still applies before that further try may start.
19. **Given** only one eligible account is on the queue and its daily collection fails with a GitHub rate limit, **When** that attempt fails and the same run is queued for a further try at the back, **Then** the further try does not start until at least 2 minutes have passed (or longer when that failure supplies a GitHub-indicated retry period), even though no other account is ahead in the queue.
20. **Given** only one eligible account is on the queue and its daily collection fails with an unexpected error, **When** that attempt fails and the same run is queued for further tries at the back, **Then** the first further try does not start until at least 3 minutes have passed, the second until at least 6 minutes after its preceding failed attempt, and the third until at least 12 minutes after its preceding failed attempt, even though no other account is ahead in the queue.
14. **Given** one of those further tries succeeds, **When** the operator reads the page, **Then** the run is a success, the kept snapshot is that try, and no remaining try starts.
15. **Given** the first attempt and all 3 further tries fail for a GitHub rate limit or an unexpected error, **When** the operator reads the page, **Then** the run is failed, with one short reason and the time that run failed. When a successful snapshot already exists, its finish time is still shown. The next eligible 05:00 UTC can start again.
16. **Given** any attempt finds that the stored access cannot be used, **When** that attempt fails, **Then** no further try starts for that occasion, the account does not rejoin the queue, and later daily collections wait until the operator signs in successfully again.
17. **Given** a daily collection has failed or is still trying again, **When** the operator looks for a retry control, **Then** this feature offers none. They can start a collection themselves with the existing start control once no collection is in progress and they are not waiting on the day's queue.
18. **Given** a daily pass is running, **When** the operator-facing app stops or is not running and the scheduled collection process keeps running, **Then** the run is not interrupted.

### User Story 7 - Skip a missed day, and follow recent sign-ins (Priority: P2)

Under the initial daily fill default, if the scheduled collection process is running at 05:00:00 UTC, that day's queue is filled then. Whether the operator-facing app is running does not fill or miss that queue. If the scheduled collection process is not running at 05:00:00 UTC, the queue is filled at the first moment it is running again at or before 05:15:00 UTC. The queue is filled only once for that occasion. If the scheduled collection process is not running at any moment from 05:00:00 UTC through 05:15:00 UTC, that day's fill is missed and the queue is not filled later that UTC day. Work already placed on the queue is still taken whenever the scheduled collection process is back and takes the next entry, including after 05:15:00 UTC, at any time of day, and including a further try waiting at the back. That scan runs only when the person is still allowed to use the product and their latest completed sign-in is still inside 30 days. Otherwise that queued scan does not run: the queue entry is removed, no failed collection is recorded, the next queued person is taken, and the page states that no scheduled collection will run, and why. The fill clock is not reapplied. A pass that was running when the scheduled collection process stopped is interrupted and does not rejoin that queue. A further try that was only waiting stays shown as in progress and still runs. The next new unattended fill under that default is the following day at 05:00 UTC, and only for a person who is eligible then. A person who completes their first hosted sign-in after that day's fill does not get an immediate unattended collection; they wait until the next scheduled fill, and they can still start one themselves before then when they can use the product. There is no catch-up fill later the same UTC day.

A scheduled collection needs both a recent sign-in and current permission to use the product. The allow lists are not the list of people who are scanned. A person who is allowed but has never completed a hosted sign-in does not get a scheduled collection. A person who was allowed, and who signed in inside the last 30 days, does not get one after they are no longer allowed. Removing a user login stops that person's daily collection. Removing an organisation login stops the daily collection for people whose saved sign-in organisations allowed them only through that organisation. A person who remains allowed by their own user login still receives one while their sign-in is inside 30 days and they are not waiting after invalid stored access. Membership is not refreshed from GitHub at queue fill for that occasion. Turning admission on with empty lists stops every daily collection. Turning admission off does not scan people who have not signed in. It stops the lists from refusing people who have signed in inside the window.

A completed sign-in starts or restarts that person's 30-day window from that sign-in. Signing in does not itself start a collection. A sign-in that does not complete does not start the window and does not lift a wait after invalid stored access. A completed sign-in does not put a person into the daily set while they are not allowed.

**Why this priority**: Catching up in the middle of the day would put the long collection back in front of the operator, which this feature exists to avoid. The operator can start a collection themselves when they want one sooner. Scanning everyone on an allow list would collect for accounts that have never signed in. Continuing to collect after someone loses access would collect for a person the product no longer lets in.

**Independent Test**: Make the scheduled collection process unavailable from 05:00:00 UTC through 05:15:00 UTC, bring it back later the same UTC day, and confirm no collection starts until the next 05:00 UTC. Separately, bring it back at 05:10:00 UTC and confirm that day's queue is filled then. Have a new person complete sign-in after 05:00 UTC and confirm no unattended collection starts until the next occasion, while a hand-started collection still works when they can use the product. Remove a person who signed in inside 30 days from admission, or turn admission on with empty lists, and confirm the next 05:00 UTC does not start a collection for them. Put a person who has never signed in onto an admission list and confirm no unattended collection starts for them. Allow the removed person again, with the sign-in still inside 30 days, and confirm the following occasion does start one.

**Acceptance Scenarios**:

1. **Given** the scheduled collection process is not running at any time from 05:00:00 UTC through 05:15:00 UTC, **When** it becomes available later that same UTC day, **Then** the missed collection does not start, and the next unattended collection is the following day at 05:00 UTC.
2. **Given** the scheduled collection process is not running at 05:00:00 UTC, **When** it is running again at 05:10:00 UTC, **Then** that day's queue is filled at that return. It is not left until the following day.
3. **Given** the scheduled collection process is running at 05:00:00 UTC and the queue is filled, **When** it stops and is running again before 05:15:00 UTC, **Then** the queue is not filled a second time. Work already queued still runs when that person is still allowed and still inside 30 days, including at a time that is not 05:00 UTC.
4. **Given** a person completes their first hosted sign-in after 05:00 UTC, **When** the rest of that UTC day passes, **Then** no unattended collection starts for them until the next 05:00 UTC.
5. **Given** that person can use the product, **When** they start a collection themselves before the next 05:00 UTC, **Then** that hand-started collection can succeed.
6. **Given** a person whose latest completed sign-in is no older than 30 days, **When** they are removed from the user list, their only admitting organisation is removed, or admission is turned on so that neither list includes them, and the next 05:00 UTC passes, **Then** no daily collection starts for them.
7. **Given** a person is added to an admission list and has never completed a hosted sign-in, **When** the next 05:00 UTC passes, **Then** no daily collection starts for them.
8. **Given** a person completes a hosted sign-in, **When** that sign-in completes, **Then** the 30-day window is measured from that sign-in and no collection starts because of the sign-in. If they are not allowed at the next 05:00 UTC, no daily collection starts then.
9. **Given** an attempt to sign in does not complete, **When** 05:00 UTC passes, **Then** that attempt does not start a 30-day window, does not lift a wait after invalid stored access, and does not by itself cause a daily collection.
10. **Given** hosted admission is on with a large allow list, and only some of those people have completed a hosted sign-in, **When** 05:00 UTC passes, **Then** no daily collection starts for a listed person who has never completed sign-in.
11. **Given** the operator-facing app is not running and the scheduled collection process is running at 05:00:00 UTC, **When** 05:00:00 UTC passes, **Then** that day's queue is still filled.
12. **Given** the operator-facing app is running and the scheduled collection process is not running at any time from 05:00:00 UTC through 05:15:00 UTC, **When** that window ends, **Then** the day is missed.

### Edge Cases

- The daily collection and a collection the operator starts are the same collection. There is one current snapshot per operator. A newer success replaces the older one, whichever way the run started.
- A daily run that is still in progress at the next 05:00 UTC, or still waiting on the previous occasion's queue, does not gain a second queue entry.
- An account with no linked repositories can still have a successful daily snapshot: success, a finish time, and a count of zero. That is different from never having run, and different from a failed first run.
- Leaving the Repositories page, being signed out, or the operator-facing app stopping or not running does not by itself mark a daily run as interrupted. Interrupted means the scheduled collection process stopped while a pass of that collection was running. Waiting on today's queue before the collection has started is not shown as in progress. A further try waiting at the back is shown as in progress, and a stop during that wait does not interrupt the run. That queued work is still taken as soon as possible after the scheduled collection process is back, and it runs only when that person is still allowed and still inside 30 days.
- The live catalogue can change after a snapshot is taken. The snapshot stays as last collected until a later collection succeeds. Reloading the live catalogue does not change the snapshot and does not start a collection.
- Repositories the Repositories page cannot already show for that operator are not added by the daily collection. Organisation-owned repositories appear only when they are already part of that personal catalogue.
- One operator's scheduled run does not count as another operator's in-progress run. Eligible people are queued at the same scheduled occasion fill. Only one scheduled collection runs at a time. A later start, at any time the process runs, is still that occasion's queued work. The operator does not see the queue or their place in it.
- More than one running copy of the scheduled collection process does not queue or collect an eligible person twice for the same occasion. Copies of the operator-facing app do not run the daily collection. The single snapshot is still written once.
- The Repositories page shows collection status and does not list the repositories inside the snapshot. The live catalogue remains the list on that page.
- The product does not keep a log of past daily occasions or past runs. A skipped occasion is not listed on its own.
- The stated fill clock time does not move to the operator's local zone. For the initial default, every hosted operator sees the same nominal fill as 05:00 UTC. The page names that time only for a queue fill that will actually include that operator. It does not use a standing sentence that a collection runs each day when this operator will not have one. Processing that queue is not limited to that hour. A queued scan does not run when, at the moment the queue reaches it, the person is not allowed to use the product or their latest completed hosted sign-in is older than 30 days. The queue entry is removed, no failed collection is recorded, and the next queued person is taken. The page states that no scheduled collection will run, and why. It does not show that run as in progress, failed, or interrupted. Those checks are not the fill schedule.
- A personal deployment that remains in the lean local posture does not gain the daily collection because it is running somewhere other than the operator's desk.
- Being allowed does not by itself add a person who has never completed a hosted sign-in. Losing permission removes a person even when their latest completed sign-in is inside 30 days. When admission is off, the lists do not refuse anyone who has signed in inside the window.
- Organisation membership for a scheduled occasion is the set of organisation logins saved from that person's last completed hosted sign-in. Those logins are compared with the organisation allow list as it stands when the queue is filled for that occasion. The product does not ask GitHub again only to check membership. Leaving or joining a GitHub organisation does not change that saved set until the next completed sign-in.
- A completed hosted sign-in sets the 30-day window. It does not cause a collection while the person is not allowed. A sign-in that does not complete does not count.
- A successful collection does not extend the 30 days. Only a completed sign-in does.
- After a daily collection fails because the stored access cannot be used, later daily occasions skip that person until they complete sign-in again. A rate limit, an unexpected error, an interruption, a missed day, or a run already in progress does not cause that skip.
- A rate limit or an unexpected error on a daily collection is tried again up to 3 times, as part of the same run. Each further try goes to the back of the queue and must wait at least the applicable minimum wall-clock delay (GitHub-indicated retry period when the product has one from a rate-limit failure, otherwise 2 minutes; unexpected-error failures use staggered minimums of 3, 6, then 12 minutes before the first, second, and third further tries) before it may start, including when this account is alone in the queue. Other accounts already ahead still run first. A sign-in or token failure is not tried again and does not rejoin the queue. The scheduled collection process stopping while a pass is running is an interruption, not one of those further tries, and that pass does not rejoin the queue. The page shows a further try waiting at the back as that same run in progress. A further try already waiting at the back is still taken after the scheduled collection process is back, and it runs only when that person is still allowed and still inside 30 days.
- The operator does not see a separate entry for each try. While a further try waits at the back, the page shows that same daily run as in progress, not as failed. A failed daily run shows one reason and when it failed, beside the finish time of the latest successful snapshot when one exists.
- This feature does not add a retry control. Collecting again by hand uses the start control the operator snapshot collection already provides. Those hand-started runs are not given the 3 further tries. While an operator is queued for the current occasion, or a collection for them is in progress, that start control does not start a collection. They wait for the queue.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: In hosted sign-in, the product MUST place the existing operator snapshot collection on a scheduled scan queue at each scheduled occasion for each person who, at fill time for that occasion, has a latest completed hosted sign-in no older than 30 days, is currently allowed to use the product, and is not waiting after a scheduled collection failed because the stored access could not be used. For the initial delivery default, occasions are once per UTC calendar day. If the scheduled collection process is running at 05:00:00 UTC on that day, the queue MUST be filled then. If it is not, the queue MUST be filled at the first moment the scheduled collection process is running again at or before 05:15:00 UTC. Those clock times govern fill only. The queue MUST be filled only once for that occasion, including when more than one copy of the scheduled collection process is running. Each eligible person MUST be queued once for that occasion and MUST be collected at most once as that occasion's work. The scheduled collection process MUST run one scheduled collection at a time across those copies. The operator-facing app MUST NOT have to be running for fill or processing. Each queued collection MUST be taken when the queue reaches that person, as soon as the process can take the next entry, without regard to time of day. It MUST run only when that person is still currently allowed to use the product and their latest completed hosted sign-in is still no older than 30 days. Otherwise that queued scan MUST NOT run: the product MUST remove that queue entry, MUST NOT record a failed collection, and MUST continue with the next queued person. The Repositories page MUST state that no scheduled collection will run, and why, and MUST NOT show that run as in progress, failed, or interrupted. Any earlier successful snapshot MUST stay unchanged. It MUST NOT have to be in progress at the fill instant. That queue MUST NOT depend on the person opening the Repositories page or choosing the start control. It MUST NOT include a person who is allowed but has never completed a hosted sign-in, or a person who is no longer allowed at fill time.
- **FR-002**: The operator MUST NOT need to be signed in, using the product, or have the operator-facing app running for that daily collection to start and to finish. In hosted sign-in a scheduled collection process, which is not the operator-facing app, MUST queue and run the daily collection. The operator-facing app being down or stopping MUST NOT miss the day and MUST NOT interrupt a daily pass. This specification does not name the host, project, or wiring of that process. The lean local posture has no scheduled collection process.
- **FR-003**: A successful daily collection MUST be the same snapshot a successful hand-started collection would keep for that operator, including the same repository facts the operator snapshot collection already records. It MUST replace the previous successful snapshot. It MUST NOT create a second snapshot or a second kind of collection.
- **FR-004**: The operator MUST still be able to start a collection from the Repositories page in hosted sign-in and in the lean local posture, except while a collection for that operator is already in progress or they are already waiting on the current day's queue. That control MUST remain separate from reloading the live catalogue.
- **FR-005**: In the lean local posture, including a personal deployment that stays in that posture, there MUST NOT be a scheduled collection process, and the product MUST NOT start a collection on a schedule, including at 05:00 UTC. The product MUST explain that nothing collects on a schedule, and that the snapshot is kept on this machine rather than promised on another machine. The operator MUST be able to collect when they ask, without being asked to add infrastructure.
- **FR-006**: In hosted sign-in, the Repositories page MUST state the real next scheduled collection for that operator, including when no collection has ever run. When the next 05:00 UTC will queue a collection for them, the page MUST name that occasion as 05:00 UTC. While they are still waiting in that day's queue and the collection has not started, the page MUST keep naming that same 05:00 UTC occasion, MUST NOT describe the day as missed, and MUST NOT show the run as in progress. When no occasion will queue a collection, the page MUST state that no scheduled collection will run, and why, and MUST NOT imply that one will run tonight or at the next 05:00 UTC. The stated time MUST be 05:00 UTC, including for an operator whose local zone is not UTC. The page MUST still show when the latest successful collection finished, whether that success was started by the operator or by the daily occasion. When further daily collections are waiting because stored access could not be used, the page MUST show that failed run and the sign-in or token reason, and MUST state that no scheduled collection will run until the operator signs in again. When the operator can still use the product, and they are not queued or in progress, the page MUST show that they can start a collection themselves.
- **FR-007**: This feature MUST NOT offer a control or a settings page to change the time, how often the collection runs, or the 30 days. It MUST NOT add a retry control. After a daily collection fails, the operator collects again by hand only through the start control the operator snapshot collection already provides.
- **FR-008**: The product MUST allow only one in-progress collection per operator, and only one scheduled collection at a time across operators and across running copies of the scheduled collection process. If a collection for that operator is already in progress when the queue would be filled for that occasion, or they are already waiting on the previous occasion's queue, that fill MUST NOT add another entry. If a scheduled collection is in progress for that operator, or they are waiting on the current occasion's queue, including at the back of the queue for a further try, the start control MUST NOT start another.
- **FR-009**: The Repositories page MUST show whether the current run was started by the operator or by the daily occasion.
- **FR-010**: Opening the Repositories page, or reloading the live catalogue, MUST NOT start a collection. The daily occasion in hosted sign-in is the only new way a collection starts.
- **FR-011**: While a daily collection is in progress, the operator MUST be able to keep using the rest of the product. If they stay on the Repositories page, the state, the start time, and the recorded count MUST update without them leaving or reloading.
- **FR-012**: A daily collection that fails or is interrupted MUST follow the operator snapshot collection: the same three short failure reasons, an interruption when the scheduled collection process stops while a pass is running, the previous successful snapshot unchanged, and in-progress recordings not presented as a new successful snapshot. The short reason MUST state that the scheduled collection stopped before it finished, and MUST NOT state that the operator-facing app stopped. The operator-facing app stopping MUST NOT mark a daily pass interrupted. That in-progress pass MUST NOT rejoin the queue. A stop while the person is only waiting on the queue, including for a further try, MUST NOT mark that run interrupted. The page MUST still show that the daily occasion started that run. When a successful snapshot exists, the page MUST show its finish time together with the failed or interrupted run.
- **FR-013**: The daily collection MUST use the access that operator already granted. If that access cannot be used, the run MUST fail at once with the sign-in or token reason, MUST NOT try that occasion again, and MUST NOT publish a new successful snapshot. After that failure, the product MUST NOT start further daily collections for that person until they complete a hosted sign-in again. That sign-in MUST lift the wait and restart the 30-day window from the new sign-in. A later daily collection MUST still require that they are currently allowed. A daily collection that fails for a GitHub rate limit or an unexpected error, or that is interrupted, MUST NOT create that wait and MUST NOT move the 30-day window.
- **FR-014**: One operator MUST NOT be able to read another operator's snapshot, collection status, or finish time, whether the run was daily or hand-started.
- **FR-015**: Under the initial daily fill default, if the scheduled collection process is not running at any moment from 05:00:00 UTC through 05:15:00 UTC, that day's queue MUST NOT be filled later the same UTC day. Returning after 05:15:00 UTC MUST NOT fill it. Work already placed on the queue MUST still be taken whenever the scheduled collection process is back and takes the next entry, including after 05:15:00 UTC and at any time of day, and including a further try waiting at the back. That scan MUST run only when the person is still allowed and their latest completed sign-in is still inside 30 days. Otherwise that queued scan MUST NOT run: the product MUST remove that queue entry, MUST NOT record a failed collection, and MUST continue with the next queued person. The fill clock MUST NOT be applied again as a reason to skip. A pass that was running when the scheduled collection process stopped MUST be interrupted and MUST NOT rejoin the queue. A further try that was only waiting MUST NOT be interrupted by that stop, and the page MUST keep showing it as in progress. A restart inside the 15 minutes after the queue was filled MUST NOT fill it again. The next new unattended fill MUST be the following day at 05:00 UTC under that default, and only for a person who is eligible then. The operator MUST still be able to start a collection themselves later that same day when they can use the product and they are not already queued or in progress.
- **FR-016**: A person who completes a hosted sign-in after 05:00 UTC MUST NOT receive an unattended collection until the next 05:00 UTC. When they can use the product, they MUST still be able to start one themselves before then. Completing the sign-in MUST NOT itself start a collection.
- **FR-017**: A scheduled collection MUST require both a completed hosted sign-in inside the last 30 days and current permission to use the product at fill time for that occasion. The allow lists MUST NOT be scanned in full. When admission is on, organisation allowance MUST be decided from the organisation logins saved at that person's last completed hosted sign-in, compared with the organisation allow list as it stands when the queue is filled for that occasion. The product MUST NOT call GitHub only to refresh that membership. A later change of GitHub organisation membership MUST NOT change eligibility until the next completed sign-in saves a new set. A person who is allowed and has never completed sign-in MUST NOT be queued. A person who is no longer allowed MUST NOT be queued, including when their latest completed sign-in is inside 30 days. Removing a user login MUST stop that person from being queued at the next fill. Removing an organisation login MUST stop queueing for a person who was allowed only through that saved organisation, and MUST NOT stop a person who remains allowed by their own user login. When hosted admission is on and both lists are empty, no scheduled fill MUST queue anyone. When hosted admission is off, the lists MUST NOT refuse a person who completed sign-in inside the window, and MUST NOT add a person who has not signed in. Allowing a person again, while their latest completed sign-in is still inside the window and they are not waiting after invalid stored access, MUST include them at the next scheduled fill. Queuing uses those checks at fill time. Running uses them again when a queued entry is about to run: allowance as it stands then, and the 30-day window from the latest completed sign-in as it stands then. If either check fails, that queued scan MUST NOT run: the product MUST remove that queue entry, MUST NOT record a failed collection, and MUST continue with the next queued person. The Repositories page MUST state that no scheduled collection will run, and why. A stored-access failure on a scan that does run remains the existing sign-in or token failure. It is not a second fill-clock rule.
- **FR-021**: Queuing a scheduled scan and running a queued scan MUST be treated as different processes. They MAY use different rules. The scheduled collection process MUST take entries on the scheduled scan queue whenever it is running. Time-of-day constraints, including the initial default at 05:00 UTC and its grace window, MUST apply only to whether and when the queue is filled for a scheduled occasion. They MUST NOT block an entry already on the queue. When an entry is about to run, including a further try at the back, the product MUST NOT run that scan if the person is not currently allowed to use the product or their latest completed hosted sign-in is older than 30 days. It MUST remove that queue entry, MUST NOT record a failed collection, and MUST continue with the next queued person. The page MUST state that no scheduled collection will run, and why, and MUST NOT keep showing that run as in progress, failed, or interrupted. Concurrency rules in this feature still apply. The specification MUST remain compatible with a later change to fill frequency or per-operator schedules without rewriting these queue-processing rules.
- **FR-018**: The product MUST NOT keep a log or list of past daily occasions. A skipped occasion is not listed on its own. The operator-facing record is the current run, the latest successful snapshot when one exists, and the statement of the next occasion or that no scheduled collection will run.
- **FR-019**: A completed hosted sign-in MUST set that person's 30-day window from that sign-in. That window alone MUST NOT cause a daily collection while the person is not allowed. A sign-in that does not complete MUST NOT start or restart the window and MUST NOT lift a wait after invalid stored access. A successful daily or hand-started collection MUST NOT by itself extend the window. A sign-in exactly 30 days before the occasion is inside the window. A sign-in older than 30 days is outside it.
- **FR-020**: When a daily collection fails because of a GitHub rate limit or an unexpected error, the product MUST try that same run again, up to 3 further tries, by placing that account at the back of the queue. The product MUST NOT start a further try until at least the applicable minimum wall-clock period has elapsed: for a rate-limit failure, at least the GitHub-indicated retry period when the product already has one from that failure, otherwise at least 2 minutes; for an unexpected-error failure, staggered minimum waits measured from that failed attempt: at least 3 minutes before the first further try, at least 6 minutes before the second further try, and at least 12 minutes before the third further try. That minimum MUST apply even when no other account is ahead in the queue. Other accounts already queued ahead MUST run before that further try. The further try MUST NOT hold those other accounts up. A try that succeeds MUST become the kept snapshot and MUST stop the remaining tries. If every try fails, the product MUST record one short reason and the time the run failed, and MUST show that beside the finish time of the latest successful snapshot when one exists. The tries MUST NOT appear as separate runs. While a further try waits at the back, the page MUST show that same run as in progress and MUST NOT show it as failed. A sign-in or token failure on any try MUST end the sequence at once and MUST NOT rejoin the queue. The scheduled collection process stopping while a pass is running MUST remain an interruption, MUST NOT be consumed as one of the 3 tries, and MUST NOT rejoin the queue. A further try already waiting at the back of the queue MUST still be taken after the scheduled collection process is back and MUST NOT be marked interrupted because of that stop. It MUST run only when that person is still allowed and still inside 30 days. The page MUST keep showing that waiting run as in progress until it succeeds, fails, or a later pass is interrupted. A collection the operator starts by hand MUST NOT receive these further tries.

### Key Entities

- **Scheduled collection process**: The part of the product that, in hosted sign-in, fills the scheduled scan queue at each occasion and processes that queue. It is not the operator-facing app. The app does not have to be running for the queue to fill or for a scheduled collection to finish. The app stopping does not interrupt a scheduled pass and does not by itself miss a fill. For the initial daily default, if this process is not running at any moment from 05:00:00 UTC through 05:15:00 UTC, that day's fill is missed; queued work from an earlier fill is still taken at any time when the process runs, and that scan runs only when the person is still allowed and still inside 30 days. If it stops while a pass is running, that pass is interrupted. If it stops while work is only queued, that work is still taken when the process is back, at any time of day, and runs only when that person is still allowed and still inside 30 days. More than one copy still queues each eligible person once per occasion. This specification does not name its host, project, or wiring. It does not exist in the lean local posture.
- **Operator snapshot**: The single current collection for one operator, as the operator snapshot collection already defines it. A daily success and a hand-started success both write this same snapshot. It does not hold a history of older collections. It is readable only by that operator.
- **Collection run**: The operator-visible state of collection for that operator: never run, in progress, succeeded, failed, or interrupted. Waiting in the day's queue before the collection has started is not shown as in progress. A further try waiting at the back is shown as that same run in progress, not as failed, and the tries are not listed. A stop while the person is only waiting, including during that further-try wait, does not make the run interrupted. A stop while a pass is running does, and that pass does not rejoin the queue. This feature adds whether the current run was started by the operator or by the daily occasion, and the statement of the next occasion that will queue a collection or that none will run. A daily run that is being tried again after a rate limit or an unexpected error stays one run until it succeeds, fails, or is interrupted, including while it waits at the back of the queue for the applicable minimum wall-clock wait. That waiting further try is still taken after the scheduled collection process is back, and runs only when that person is still allowed and still inside 30 days and the minimum wait has elapsed. Timing, counts, and the short reason stay as the operator snapshot collection already defines them. The recorded failure reason is shown with the finish time of the latest successful snapshot when one exists.
- **Scheduled occasion (queue fill)**: The moment the product fills the scheduled scan queue for a planning cycle. The initial delivery default is one fill per UTC calendar day, nominally at 05:00 UTC, for people whose latest completed hosted sign-in is no older than 30 days at fill time, who are currently allowed to use the product, unless scheduled collections are waiting because stored access could not be used. Eligible people are placed on one queue at 05:00:00 UTC if the scheduled collection process is running then, otherwise at the first moment it is running again at or before 05:15:00 UTC, under that default. Those times bound fill only. Collections for that occasion's queue run one at a time when the process is running, at any time after fill. A person is queued and collected once per occasion even when more than one copy of the scheduled collection process is running. The operator-facing app does not have to be running, and it does not perform the fill. It is not a scan of everyone who is allowed. It is not a separate snapshot. It does not exist in the lean local posture. A missed or skipped fill is not stored as its own record. The operator does not see the queue.
- **Sign-in window**: The 30 days after a person's latest completed hosted sign-in. Only a completed sign-in moves it. A collection does not. That same completed sign-in saves the organisation logins used later to decide organisation allowance. The daily occasion does not replace those logins.


## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: On a UTC day when the scheduled collection process is running at 05:00:00 UTC, or is running again by 05:15:00 UTC, each person whose latest completed hosted sign-in is no older than 30 days, who is currently allowed at fill time, and who is not waiting after invalid stored access, is placed on the queue once, with nobody opening the Repositories page and nobody choosing the start control. Their collection runs when the queue reaches them, as soon as the process can take the next entry, which may be any time that day or later, only if they are still allowed and their latest completed sign-in is still inside 30 days. If either check fails then, that queued scan does not run: the entry is removed, no failed collection is recorded, and the next queued person is taken. Time of day does not skip a queued scan that still passes those two checks. Only one scheduled collection is in progress at a time, including when more than one copy of the scheduled collection process is running. Each eligible person is queued and collected once for that occasion. A person who does not open the product that day is still queued when those conditions hold, including when the operator-facing app is not running. That day's fill is missed when the scheduled collection process is not running across the fill window, even if the app is running; work already on the queue from an earlier fill still processes at any time. A person who has not signed in inside 30 days is not queued, including when they are allowed. A person who is no longer allowed at fill time is not queued.
- **SC-002**: After that daily run succeeds, the kept snapshot matches the catalogue a hand-started collection would have kept for that same operator, including a count of N when that catalogue contains N linked repositories. The Repositories page shows success, the finish time, and that count, and does not list the entries.
- **SC-003**: A second hosted operator sees none of the first operator's repository entries, finish time, or collection status from either a daily run or a hand-started run.
- **SC-004**: After a successful daily collection, the operator can start another collection from the Repositories page, and that later success replaces the daily snapshot.
- **SC-005**: In the lean local posture, no collection starts at 05:00 UTC. The page states that nothing collects on a schedule and that the snapshot is kept on this machine rather than promised on another machine. The operator can complete one collection when they ask, without adding infrastructure.
- **SC-006**: When a collection for that operator is already in progress at 05:00 UTC, or they are already queued, no second collection is added. When a daily collection is in progress or they are waiting on the day's queue, the start control does not start a second collection. When two people are queued, only one daily collection is in progress at a time, and the second starts as soon as possible after the first finishes. An operator who stays on the page sees the recorded count rise before the run finishes, without leaving or reloading, and sees that the daily occasion started it.
- **SC-007**: After a failed daily run, the operator sees exactly one of the short reasons (a sign-in or token problem, a GitHub rate limit, or an unexpected error) and when it failed, and, when a successful snapshot exists, its finish time as well. The previous successful snapshot is unchanged. After the scheduled collection process stops while a pass is running, the next visit shows the run as interrupted and not as in progress, and that pass does not rejoin the queue. A stop while the person is only waiting on the queue, including for a further try, does not show that run as interrupted, and that queued work is still taken after the scheduled collection process is back, and runs only when that person is still allowed and still inside 30 days.
- **SC-012**: A daily collection that hits a GitHub rate limit or an unexpected error is tried again up to 3 times by going to the back of the queue and waiting the applicable minimum before each further try may start, as one run (rate-limit failures use the GitHub-indicated retry period when known, otherwise 2 minutes; unexpected-error failures use staggered minimums of 3, 6, then 12 minutes). While a further try waits, the page shows that same run as in progress, not as failed, and does not list the tries. When only one account is queued, the further try does not start immediately after the failure. Other accounts already queued ahead run before that further try. A try that succeeds is the kept snapshot. If all tries fail, the next eligible day can still start, and the page offers no separate retry control. A sign-in or token failure is not tried again that occasion and does not rejoin the queue. A collection the operator starts by hand is not given those further tries.
- **SC-008**: If the scheduled collection process is not running at any time from 05:00:00 UTC through 05:15:00 UTC, that day's queue is not filled later that same UTC day. If it is running again by 05:15:00 UTC, that day's queue is filled then and is not filled a second time. Work already queued is still taken as soon as possible afterwards, and runs only when that person is still allowed and still inside 30 days. A person who first completes sign-in after the queue was filled waits until the next 05:00 UTC for an unattended collection and, when they can use the product, can still complete a hand-started collection before then.
- **SC-009**: In hosted sign-in, before any collection has run and after one has, the operator can read either the next 05:00 UTC that will start a collection for them, or that no scheduled collection will run and why. After a daily failure because stored access could not be used, the page shows that failure and does not say a collection will run tonight. When a successful collection exists, its finish time is still shown, whether the operator started it or the daily occasion did. They have no control that changes the time, how often, or the 30 days.
- **SC-010**: A person who is allowed and has never completed sign-in receives no daily collection. A person removed from the user list, or refused because their only admitting organisation was removed, or facing empty lists while admission is on, receives none even when their latest completed sign-in is inside 30 days. When admission is off, a person who completed sign-in inside 30 days and is not waiting after invalid stored access still receives one.
- **SC-011**: After a daily collection fails because stored access cannot be used, no later 05:00 UTC starts a collection for that person until they complete sign-in again. That sign-in restarts the 30 days. A rate-limit failure, an unexpected error, or an interruption does not stop the next eligible day.

## Scope

### In scope

- Filling a scheduled scan queue once per UTC day at 05:00 UTC (initial default) for each person who has completed a hosted sign-in inside the last 30 days and who is currently allowed at fill time, without that person being present and without the operator-facing app running. A scheduled collection process that is not that app fills and processes that queue. How it is hosted is not part of this specification. One scheduled collection runs at a time. Processing is not limited to the fill hour. A queued scan does not run when that person is no longer allowed or is outside the 30-day window at the moment the queue reaches them. That entry is removed, no failed collection is recorded, and the next queued person is taken.
- Keeping the hand-started collection on the Repositories page.
- Telling the hosted operator, on that page, the next 05:00 UTC that will start a collection for them, or that no scheduled collection will run and why, including when none has ever run, and still showing when the last successful collection finished.
- Stopping further daily collections after stored access cannot be used, until the next completed sign-in, which restarts the 30 days.
- Trying a daily collection again up to 3 times, by sending that account to the back of the queue and waiting the applicable minimum before each further try (GitHub-indicated or 2 minutes for rate limits; staggered 3, 6, and 12 minutes for unexpected errors), when the failure is a GitHub rate limit or an unexpected error, so other accounts are not held up and brief failures are not retried instantly when the queue is small, and recording one final reason beside the finish time of the last successful snapshot.
- Showing whether the current run was started by the operator or by the daily occasion.
- Leaving the lean local posture on demand only, with the existing explanation that nothing collects on a schedule.
- Using the same success, failure, interruption, replacement, and isolation behaviour the operator snapshot collection already has.

### Out of scope

- A second scanner, a second snapshot, or a different set of repository facts.
- Any schedule in the lean local posture, and any scheduled collection process in that posture.
- Naming the host, project, or wiring of the scheduled collection process.
- Requiring the operator-facing app to be running for the daily collection to be queued or to finish.
- A control or settings page for the operator to change the fill time, how often the queue is filled, or the 30 days. This delivery keeps the initial default of one fill per UTC day at 05:00 UTC for people who completed sign-in inside the last 30 days and who are currently allowed at fill time. A later feature may change that default or offer per-operator schedules without contradicting queue-processing rules in this specification.
- Filling the queue after 05:15:00 UTC when the scheduled collection process was not running at any time from 05:00:00 UTC through 05:15:00 UTC.
- A stored history of daily occasions, past runs, or the individual tries inside one daily run.
- A retry control, or any other way to collect again by hand beyond the start control the operator snapshot collection already provides.
- Automatic further tries for a collection the operator started by hand.
- Community-standard gaps, FUNDING status, and any later facts the operator snapshot collection left for other features.
- Writing or copying repository files to GitHub.

## Assumptions

- The daily collection belongs only to hosted sign-in and is performed by a scheduled collection process that is not the operator-facing app. The app does not have to be running for that collection to be queued or to finish. This specification does not name the host, project, or wiring of that process. The lean local posture, including a personal deployment that stays in that posture, has no scheduled collection process and does not get a schedule. That is the split this request asked for between the shared sign-in posture and use on the operator's own machine.
- The daily set is every person who has completed a hosted sign-in at least once in the last 30 days and who is currently allowed to use the product, minus anyone waiting after a daily collection failed because stored access could not be used. There is no separate choice to turn the schedule on or off in this feature.
- Current permission uses the existing hosted admission rules at fill time for each scheduled occasion, and again when a queued entry is about to run and when the Repositories page states the next occasion. At fill, when admission is on, a person is allowed when their user login is listed or an organisation login saved from their last completed sign-in is on the organisation list as it stands at that fill instant. At dequeue and at page read, the same rule uses those allow lists as they stand at that current moment, still compared only with organisation logins saved from the last completed sign-in. The product does not ask GitHub again only to check membership, so leaving or joining a GitHub organisation takes effect at the next completed sign-in. When admission is off, those lists do not refuse anyone. The lists are not scanned in full: a listed person who has never completed sign-in is not scanned. A person who was allowed and is then refused is not queued at the next fill, even inside the 30 days. Removing an organisation from the allow list stops queueing only for people who have no remaining way to be allowed from their user login or their saved organisation logins. Allowing someone again does not require a new sign-in while the existing window is still open and they are not waiting after invalid stored access.
- The page names the next 05:00 UTC only when that occasion will queue a collection for that operator. If today's 05:00 UTC has not yet passed and they are eligible for it, that is the named occasion. If they are still waiting in today's queue, that remains the named occasion even after 05:00 UTC. If today's occasion was missed because the scheduled collection process was not running at any time from 05:00:00 UTC through 05:15:00 UTC (the operator-facing app being down does not, by itself, miss the day), or was skipped because a run was already in progress, the candidate is the following UTC day, and it is named only when they will still be eligible then. Eligibility means a completed sign-in no older than 30 days at that occasion, currently allowed, and not waiting after invalid stored access. A credential failure, a closed window, or a loss of permission is stated as no scheduled collection, not as a time that will still run.
- "Signed in" in this feature means a hosted sign-in that completed. A sign-in that does not complete does not open or restart the 30 days and does not lift a wait after invalid stored access.
- The 30 days are measured at fill time for each scheduled occasion from the latest completed sign-in. Under the daily default that instant is 05:00 UTC unless fill happens later inside the grace window. A sign-in exactly 30 days earlier is still inside the window. A sign-in older than 30 days is outside it. A successful collection does not move the window. Only a completed sign-in does.
- The wait after invalid stored access applies only when a daily collection fails with the existing sign-in or token reason. That failure is not tried again that occasion. The failing run still happens and stays visible, including the finish time of the latest successful snapshot when one exists. The page does not imply that another collection will run tonight. Later occasions do not start another run until a completed sign-in, and only when the person is also currently allowed. A rate limit, an unexpected error, an interruption, a missed day, or a run already in progress does not start that wait.
- "Up to 3 times" means up to 3 further tries after the first attempt, so at most 4 attempts in that run. Each further try goes to the back of the queue. Before it may start, the product waits at least the applicable minimum wall-clock period: for a rate-limit failure, at least the GitHub-indicated retry period when the product already has one from that failure, otherwise at least 2 minutes; for an unexpected-error failure, staggered minimum waits measured from that failed attempt: at least 3 minutes before the first further try, at least 6 minutes before the second further try, and at least 12 minutes before the third further try. Other accounts already queued ahead run first. When no other account is ahead, the further try still must not start until that minimum has elapsed; queue position alone is not enough. The wait is not held in front of those other accounts, and it is not a wait until the next day. The operator cannot see the queue, their place in it, or a list of tries. While a further try waits, the page shows that same run as in progress. Each further try is a fresh pass of the same collection. Only a pass that succeeds replaces the snapshot. A sign-in or token failure on any attempt ends the sequence immediately and does not rejoin the queue.
- A completed sign-in after 05:00 UTC does not start a catch-up unattended collection later that same UTC day. The next unattended chance is the following 05:00 UTC.
- For the initial delivery default, the named fill clock time is 05:00 UTC for every operator. It is not 05:00 in the operator's local zone. How often the queue is filled is once each UTC day. A later feature may let the operator change fill time or frequency; this feature does not. Queue processing is not tied to that hour.
- Eligible people are placed on one queue at each scheduled fill. Under the daily default that is nominally 05:00 UTC. One scheduled collection runs at a time. A run that starts at any later time is still that occasion's queued work, processed when the queue reaches that person. If a collection for that operator is already in progress, or they are already on the previous occasion's queue, the new fill does not add another entry. When more than one copy of the scheduled collection process is running, each eligible person is still queued once and collected once for that occasion.
- If the scheduled collection process is running at 05:00:00 UTC, the queue is filled then. If it is not, it is filled at the first moment the scheduled collection process is running again at or before 05:15:00 UTC, and only once. If it is not running at any moment in that span, the day is missed and the queue is not filled later. A queue that was already filled is still taken after the scheduled collection process returns, including a further try waiting at the back. The scan runs only when that person is still allowed and still inside 30 days. If either check fails, the entry is removed, no failed collection is recorded, and the next queued person is taken. A pass that was running when the scheduled collection process stopped is interrupted and does not rejoin. A further try that was only waiting stays shown as in progress until it runs, or until those run rules remove it.
- The daily collection reads the same personal catalogue as a hand-started collection, and it uses the access the operator already granted. It does not ask them to sign in again at 05:00 UTC. If that access cannot be used, the existing sign-in or token reason applies.
- What a snapshot contains, which short reasons the operator sees, and the rule that only the latest success is kept stay as defined for the operator snapshot collection. This feature changes when a collection can start, and it records which of the two starts was used.
- The overnight start is there so a collection that grows slower over time does not have to be watched. The run may still be in progress after 05:00 UTC. The operator is not required to stay on the page until it finishes.
- Operator-facing text uses UK English.
- The Repositories page remains the only place the operator reads collection status and starts a collection by hand.
