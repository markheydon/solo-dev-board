# Feature Specification: Scheduled snapshot collection

**Feature Branch**: `002-scheduled-snapshot-collection`

**Created**: 2026-11-23

**Status**: In progress. The 2026-11-25 revision adds a stored account scan status. While a hosted scan is `running` and still working, the process doing that scan records a fresh liveness mark at least once every 60 seconds until that scan records `finished` or `suspended`. If no liveness mark has been recorded for more than 5 minutes, callers are told `stalled` and the stored status stays `running`. Daily fill rules are unchanged. That revision is specified here. Phases 13–22 in tasks.md (T120–T154) are the open backlog. Phases 1–12 are delivered.

**Input**: User description: "Follow-on to the operator snapshot collection. In hosted sign-in, run that same collection unattended on a schedule so the operator does not have to request it and does not have to wait on screen while a longer collection runs. The current schedule asks for that work once per UTC day at 05:00 UTC. That is only how often this delivery asks. A fill may run at any time, and each fill queues the people who are eligible then and are not already queued or in progress, including after an earlier success the same day. Each queued request is picked up and run whenever the scheduled collection process is running. A later schedule may ask more often, including every 10 minutes. The lean local posture does not get a schedule. Starting a collection by hand remains."

**Revision 2026-11-25**: At any time of day or night, the operator can read an accurate current state for a scheduled scan of their account. That state is stored from what actually happened. It is not inferred from a best guess about whatever data happens to be available. Each account seen under the existing logged-in-within-30-days rule has a stored status, the last scan time (empty if a scan has never run), the last result (success, failure, or empty), and a result comment. While a hosted scan is `running` and still working, the process scanning that account records a fresh liveness mark at least once every 60 seconds until that scan records `finished` or `suspended`. If no liveness mark has been recorded for more than 5 minutes, every process that asks for that account's scan status is told `stalled`, not `running`. `stalled` is reported for that condition and is not stored. The stored status stays `running` until a new scan is queued or started by hand. A reported `stalled` account does not count as in progress. A later fill queues that account when the other eligibility rules allow, and that new queue entry sets the stored status to `scheduled`. The operator may start a collection by hand while the account is reported `stalled`. That hand-started collection sets `running` and updates the liveness mark. The earlier queue entry does not rejoin. The 30-day, permission, and stored-access rules for who is queued are unchanged.

## Clarifications

### Session 2026-11-25

- Q: How should the product describe the current state of a scheduled scan? → A: From a stored account scan status, written from what actually happened. The Repositories page reads that record at any time of day or night. It does not infer running, finished, failed, or suspended from the clock, from a missing visit, or from the absence of a worker.
- Q: Who has a stored status? → A: Each account the product has already seen under the daily fill's logged-in-within-the-last-30-days rule. The record is created when that account is first recorded for later scanning, including when the access the scanner will use is stored. The default is `never run`. A later sign-in does not reset a record that already moved on. The record stays readable after the 30-day window closes. Fill eligibility is unchanged.
- Q: What does the record hold? → A: The status; the date and time the last scan was run, empty when none has run; the result of that last run, which is success, failure, or empty; and a result comment. The comment is Success when that last run succeeded. When it failed, the comment states why. When status is suspended because the scan was not run, the last run time, result, and result comment stay as they were. The record states why with `suspensionReason` `notAllowed`. That value is a fact, not a second result comment. The page maps it to the fixed comment that they are not allowed.
- Q: Which statuses are real? → A: `never run`, `scheduled`, `running`, `finished`, and `suspended`. A further status may be stored only when it is a real state the page or another process must show. A status must not stand in for missing information. `stalled` is not stored. It is reported when the stored status is `running` and no liveness mark has been recorded for more than 5 minutes.
  - `never run`: the default for a new record. No scan has run.
  - `scheduled`: a queue entry exists and is waiting for the worker, including a further try at the back of the queue. An entry that exists but is not yet visible still counts. If no entry exists at all, the next live scheduled collection process restores the status from the last result before the fill, as FR-022 describes.
  - `running`: the worker has taken that queue entry and has not yet recorded a terminal status.
  - `finished`: the worker has finished that queue entry. The result is success or failure, with the matching comment.
  - `suspended`: the worker took the entry and the scan cannot run again until the stated block is resolved. Either the account is no longer allowed (`suspensionReason` `notAllowed`, and the last run time, result, and result comment stay as they were), or the scan was attempted and failed because stored access cannot be used and no newer worker refresh token is already stored (result failure and the sign-in or token comment, with `suspensionReason` empty). When a newer worker refresh token is already stored, that same failure is `finished`, the failure stays visible, and the wait is not set.
- Q: What if the worker crashes after it has taken a job? → A: The stored status stays `running`. While the process is scanning that account it updates a liveness mark. If no liveness mark has been recorded for more than 5 minutes, every process that asks for that account's scan status is told `stalled`, not `running`. `stalled` is reported only. It is not stored. The last scan time, last result, and result comment stay as they were. The earlier queue entry does not rejoin because the mark lapsed. A reported `stalled` account does not count as in progress. A later fill queues that account when the other eligibility rules allow, and that new queue entry sets the stored status to `scheduled`. The operator may start a collection by hand while the account is reported `stalled`. That hand-started collection sets `running` and updates the liveness mark. The earlier queue entry does not rejoin. Where earlier text called this an interruption, or a stored finished failure, callers are told `stalled`.
- Q: Does a further try waiting at the back still look in progress? → A: No. Waiting on the queue is `scheduled`. `running` applies only while the worker has taken the entry. `finished` applies when the try sequence has ended. Where earlier text says a waiting further try is shown as in progress, this session replaces that display.
- Q: Does loss of permission still record no collection outcome? → A: The scan does not run, the queue entry is removed, and the next account is taken. The stored status becomes `suspended`, with `suspensionReason` `notAllowed`. The last scan time, result, and result comment are not overwritten, because no scan ran. Any earlier successful snapshot stays unchanged. The page shows `suspended` and that reason. It does not show `running`, and it does not present a failed snapshot. Where earlier text says no failed collection is recorded and the page must not show the run as in progress, failed, or interrupted, this session replaces the display and the stored status. It does not change the decision not to run the scan.
- Q: Does this change the daily fill? → A: No. The daily fill still queues from the rules already in this specification. This session is the stored status, and the worker's duty to keep that status true.
- Q: When an account's scan is reported as `stalled`, should the next fill still skip that account? → A: No. A reported `stalled` account does not count as in progress. The next fill may queue it when the other eligibility rules allow, which sets the stored status to `scheduled`. The operator may also start a collection by hand, which sets `running` and must update the liveness mark again. The earlier queue entry does not rejoin.
- Q: After an account has been reported as `stalled`, may the process that was already scanning it still record that scan's real result? → A: Yes, until a newer scan for that account is queued or started by hand. That result is the real success or failure. A fresh liveness mark from that same pass before a newer scan starts means callers are told `running` again. Once a newer scan has set `scheduled` or a new `running`, that earlier pass must not change the stored status, the liveness mark, or the snapshot.
- Q: If an account's stored status is `scheduled` but there is no queue entry for that account, what should the product do? → A: The next live scheduled collection process restores the status from the last result before it decides who to queue. An empty last result sets `never run`. Any other last result sets `finished`. It does not add a failure comment. The same fill may then queue the account under the existing rules. An entry that exists but is not yet visible, including a further try waiting for its minimum delay, still counts as a queue entry.
- Q: When a hosted scan for one account is stored as `running` and the process doing that scan then dies, when may another live process record a finished failure solely because that process died? → A: It must not. While that process is scanning the account it updates a liveness mark. If the stored status is `running` and no liveness mark has been recorded for more than 5 minutes, every downstream process that asks for that account's scan status is told `stalled`. `stalled` is reported for that condition and is not stored. The stored status stays `running` until a new scan is queued or started by hand. A reported `stalled` account does not count as in progress. A later fill queues that account when the other eligibility rules allow, and that new queue entry sets the stored status to `scheduled`. The operator may start a collection by hand while the account is reported `stalled`. That hand-started collection sets `running` and updates the liveness mark. The earlier queue entry does not rejoin.
- Q: While a hosted scan is still working, how often must that process record a fresh liveness mark? → A: At least once every 60 seconds until the scan records a terminal status. In this feature that terminal status is `finished` or `suspended`. A scan that is still working and keeps that cadence is told `running`, not `stalled`. The same duty covers a queue scan and a hand-started hosted scan.
- Q: When an overnight scan has gone quiet for more than 5 minutes, and a scheduled fill and the operator's start control both try to collect at the same moment, how many new scans may run? → A: Exactly one. The first to set `scheduled` or a new `running` wins; every other attempt does not start a second scan. That includes another copy of the scheduled collection process.
- Q: When a scheduled scan refreshes that operator's GitHub access and GitHub issues a new refresh token, how should the product keep them signed in in the browser? → A: The scheduled scan uses a separate worker credential, so renewing it cannot spend the refresh token that keeps the browser signed in. The browser keeps the current sign-in. The auth cookie remains the interactive session. A successful scheduled snapshot still matches a hand-started collection for that operator.
- Q: When someone completes hosted sign-in, which GitHub credential should the overnight collection keep for later scans? → A: During that same hosted sign-in, after the browser refresh token is stored, send them through GitHub a second time on the existing GitHub App and store only that authorisation's refresh token for the scheduled collection. The browser keeps the different refresh token from the first authorisation. The overnight scan may renew only its own token.
- Q: When a hosted sign-in stores both the browser refresh token and the worker refresh token, how does the operator authorise that worker token? → A: During that same hosted sign-in, send the operator through GitHub a second time on the existing GitHub App. Store only that second authorisation's refresh token as the worker token. One GitHub response is never split into two tokens. If they cancel the second authorisation, or it stores no worker token, sign-in is still complete and the browser token stays.
- Q: If that second GitHub authorisation leaves the browser refresh token unusable, what should the product do? → A: Keep a worker token only when the browser refresh token still works after that second authorisation. If it does not, discard the worker token and send them through GitHub again to restore the browser token. Sign-in is complete once the browser token works. The worker token stays missing until a later authorisation stores one without breaking the browser token. The same check applies when they authorise a worker token from the Repositories page.
- Q: If hosted sign-in stores the browser refresh token but does not store the worker refresh token, has that person completed sign-in? → A: Yes. The browser session is a completed sign-in. The next overnight scan fails with the sign-in or token reason until the worker refresh token is stored again.
- Q: If you are still signed in and you successfully refresh only the worker token used for overnight scanning, should that end the wait for the next scheduled scan without moving the 30-day sign-in window? → A: End the wait. Leave the 30-day window and the saved organisation list as they were. Do not start a scan by itself.
- Q: While you are still signed in, when should the app ask you to refresh only the worker token? → A: On the Repositories page, as soon as you are signed in and the worker token is missing or the overnight scan has failed because it cannot be used. You choose the refresh. You stay signed in if you cancel or it fails.
- Q: If a scheduled scan is already queued or already running when you refresh the worker token, what should that scan do? → A: A queued scan that has not started uses the new token when it is taken. A scan already running keeps the token it started with. If that running scan then fails because of the old token, and a newer worker token is already stored, the failure is shown and the wait is not set again.
- Q: When a scheduled scan is already running and GitHub issues a replacement for the worker refresh token that scan started with, and the operator has already stored a newer worker token, which worker token should stay stored? → A: The operator's newer worker token stays stored. The running scan does not write a rotated refresh token over it.
- Q: What human-friendly text should the page, or any other process, receive for the current scheduled-scan status and for whether a collection will run? → A: Callers still receive the reported status token. They also receive the fixed sentences in FR-025. An unattended run is called the overnight collection in the schedule wording. The status sentences do not say who started the run. A success includes when it finished and how many repositories were saved. A failure includes when it failed and one short reason. When a collection will run, the text says only that the next collection runs overnight. It does not name 05:00 UTC, tonight, today, or the following day. 05:00 UTC remains when this delivery asks for a fill.

- Q: When the page says you started a collection or the overnight collection started it, is that fact saved on the account scan status, or worked out at the moment the page is read? → A: Do not add that fact to the account scan status for display. The stored status does not already hold it, so the human-friendly text does not say who started the run.

- Q: When you start a collection yourself while signed in, which GitHub access should that scan use? → A: The signed-in session. Overnight scans use only the worker token. A missing or unusable worker token does not stop the collection you start.

- Q: When you refresh only the overnight token, should that send you through GitHub again, store only the new overnight token, and leave your current sign-in, the 30-day window, and the saved organisation list unchanged? → A: Yes. A second GitHub authorisation stores only the worker token. It does not refresh the browser token, does not sign them out, does not complete hosted sign-in, does not move the 30-day window, and does not replace the saved organisation list.

### Session 2026-11-24

- Q: Does "once a day" forbid filling the queue or running a scheduled scan more than once on the same UTC day? → A: No. Once a day at 05:00 UTC is only how often this delivery asks for a fill. It is not a cap and it is not a time window in which a fill is allowed. Whenever a fill runs, it queues every eligible person who is not already queued or in progress, including someone whose scan already succeeded earlier that day. A later schedule may ask more often, including every 10 minutes; this specification must not forbid that. The product then picks up each queued request and runs the scan. It does not add a second entry while that person is already queued or a scan for them is in progress. A failure because stored access cannot be used still waits until the worker refresh token is stored again. The phrase "5 p.m." in the request that recorded this answer is the existing planned time of 05:00 UTC, not 17:00.
- Q: Does wall-clock time restrict when queued scheduled collections run? → A: No. Once an operator is on the scheduled scan queue, processing proceeds whenever the scheduled collection process is running, at any time of day or night. Wall-clock time also does not restrict when a fill may run. 05:00 UTC is only when this delivery asks. Clock time does not remove an entry already on the queue.
- Q: What does 05:00 UTC mean in this feature? → A: It is the time this delivery asks for a fill, once per UTC calendar day. It is not a limit on when a fill may run, when queued work may run or finish, or how many times a person may be queued that day. A fill at any other time uses the same eligibility rules, including for someone whose scan already succeeded earlier that day. Changing how often the schedule asks (for example every 10 minutes) may arrive in a later feature; this specification must not forbid that.
- Q: When are eligibility rules (admission, 30 days, stored access, and the rest) evaluated for placing someone on the scheduled scan queue? → A: When the queue is filled for that occasion and when the product states the next occasion on the Repositories page. Those rules prevent someone from being placed on the queue when they fail. Clock time does not, on its own, remove an entry already on the queue.
- Q: Are the rules for placing a scan on the queue the same as the rules for running a scan that is already queued? → A: No. Each fill, at whatever time it runs, uses the 30-day sign-in window, admission, and stored-access rules at that moment, and skips anyone already queued or in progress. It does not skip someone because an earlier scan succeeded. Running a queued scan is not limited by time of day or by how long the message has waited. The worker attempts the scan when it picks up the entry unless the person is no longer allowed to use the product. The 30-day window is not re-checked at dequeue. Stored access that cannot be used is a recorded sign-in or token failure, not a silent skip.
- Q: When a queued scan is reached and that person is no longer allowed to use the product, what should happen to that queue entry? → A: Do not run it. Remove the queue entry. Do not record a failed collection. Continue with the next person. The Repositories page states that no scheduled collection will run, and why. Any earlier successful snapshot stays unchanged. The page shows suspended and the fixed comment for `suspensionReason` `notAllowed`, and does not show the scan as running or as a failed snapshot. If the scan is attempted but stored access cannot be used, that follows the existing sign-in or token failure rules for a run that starts.
- Q: After a rate-limit or unexpected-error failure on a scheduled collection, must a further try wait in wall-clock time as well as going to the back of the queue (for example when this account is alone in the queue)? → A: Yes. Each further try still goes to the back of the queue. Before that further try may start, a minimum wait applies. For a GitHub rate-limit failure, the product waits at least the GitHub-indicated retry period when it already has one from that failure, otherwise at least 2 minutes. For an unexpected error, staggered minimum waits apply (3, 6, then 12 minutes; see later clarification). Other accounts still queued ahead run first. When no other account is ahead, the further try must not start until that minimum wait has elapsed.
- Q: What fixed minimum wall-clock delay should scheduled further tries use when a rate-limit failure does not include a usable GitHub retry period, and for every unexpected-error further try? → A: 2 minutes for rate-limit failures without a GitHub-indicated retry period only (see stagger rule below for unexpected errors).
- Q: For scheduled further tries after an unexpected error (not a GitHub rate limit and not a failure that already supplies a known retry time), what minimum wait should apply before each further try may start? → A: Staggered minimum waits measured from that failed attempt: 3 minutes before the first further try, 6 minutes before the second further try, 12 minutes before the third further try. Each further try still goes to the back of the queue.

- Q: When the daily fill runs at any time of day, should it add every eligible person who is not already queued or in progress, even if their scan already succeeded earlier that same day? → A: Yes. Each fill queues everyone who, at that moment, has a latest completed hosted sign-in inside 30 days, is currently allowed, is not waiting because stored access could not be used, and is not already queued or in progress. That includes someone whose scan already succeeded earlier that day. The time of day does not decide whether a fill may run, and there is no extra wait after a previous fill or a finished scan. How often the product asks for a fill is separate. This delivery still asks once per UTC day at 05:00 UTC. A later change may ask more often, including every 10 minutes. The fill rules stay the same.

- Q: When a scheduled collection is taken from the queue and the stored access cannot be used, should the product record a failed collection with the sign-in or token reason, or drop that queue entry and record no failure? → A: Record a sign-in or token failure, stop further tries, and pause later scheduled collections until the worker refresh token is stored again. When they are no longer allowed, remove the queue entry, set the stored status to suspended with `suspensionReason` `notAllowed`, and do not overwrite the last scan time, result, or result comment because no scan ran.
- Q: When someone has more than one reason that no scheduled collection will run, which reason should the Repositories page state? → A: One schedule sentence, in this order: not allowed, otherwise the stored-access wait, otherwise the closed 30-day window. When the stored-access wait is set, still show that failed run even if the schedule sentence says they are not allowed.

## User Scenarios & Testing *(mandatory)*

**Scheduling model (all stories below):** In hosted sign-in, each **daily fill** places eligible people on a **scheduled scan queue**. Eligible means a latest completed hosted sign-in inside 30 days at that fill, currently allowed, not waiting because stored access could not be used, and not already queued or in progress. A scan that already succeeded earlier that day does not remove someone from that set. The **current schedule** asks for a fill once per UTC calendar day, nominally at 05:00 UTC. That is how often this delivery asks, not a limit on when a fill may run. A fill at any other time uses the same rules. A later schedule may ask more often, including every 10 minutes. **Queue processing** is separate: each queued request, including retries at the back, is taken whenever the scheduled collection process is running, without regard to time of day or night, and without regard to how many fills have already happened that day. A collection does not have to start or finish in the same hour as the fill. When the queue reaches an entry, the worker attempts that scan unless the person is not currently allowed to use the product. The 30-day sign-in window is enforced only when the queue is filled, not when a message is picked up. If the person is no longer allowed, the product removes that queue entry, sets the stored status to suspended with `suspensionReason` `notAllowed`, does not overwrite the last scan time, result, or result comment because no scan ran, and continues with the next person. The Repositories page states that no scheduled collection will run, and why. If stored access cannot be used, the run fails with the sign-in or token reason, further tries stop, and later scheduled collections wait until the worker refresh token is stored again. That failed run stays visible, and any earlier successful snapshot stays unchanged. Those are run rules, not the fill clock. Scenarios below name 05:00 UTC where they exercise that default fill; they are not claiming that processing is limited to that hour.

**Account scan status.** In hosted sign-in the page, and any other part of the product that needs the current scan state, reads one stored record per account. Already queued or in progress means that stored status is `scheduled`, or `running` while callers are told `running`. A reported `stalled` account is not queued and is not in progress. The page shows `running` only while the worker has taken the entry and a liveness mark has been recorded within the last 5 minutes. If the stored status is `running` and no liveness mark has been recorded for more than 5 minutes, the page and any other process that asks are told `stalled`, with the human-friendly text in FR-025. A further try waiting on the queue is `scheduled`. User Story 8, FR-022, and FR-023 are authoritative for that record. Sentences earlier in this specification that disagree with those three are replaced by them. The 30-day, permission, and stored-access rules for who is queued are not replaced. A reported `stalled` account is not already in progress.

### User Story 1 - Collect overnight without the operator waiting (Priority: P1)

In hosted sign-in, the collection the operator can already start by hand is also placed on the scheduled scan queue at each scheduled occasion. The current schedule asks for that fill once per UTC day at 05:00 UTC. A fill at any other time uses the same eligibility rules, including for someone whose scan already succeeded. One scheduled collection runs at a time across the queue. A person's collection runs when the queue reaches them, as soon as the scheduled collection process can take the next entry, which may be any time after they were queued, including days later if the message has waited, provided they are still allowed to use the product. If stored access cannot be used, the run fails with the sign-in or token reason, further tries stop, and later scheduled collections wait until the worker refresh token is stored again. If they are no longer allowed, that queued scan does not run. The product removes that queue entry, sets the stored status to suspended with `suspensionReason` `notAllowed`, does not overwrite the last scan time, result, or result comment because no scan ran, and continues with the next person. The Repositories page states that no scheduled collection will run, and why. Any earlier successful snapshot stays unchanged. Passing the fill clock is not what decides that. It does not have to be in progress at the fill instant. The queue includes each person who, at fill time for that occasion, has completed a hosted sign-in at least once in the last 30 days, is currently allowed to use the product, and is not waiting because a scheduled collection failed when the stored access could not be used. Being allowed is not enough on its own. A person who is allowed but has never completed a hosted sign-in is not included, so a long allow list is not scanned in full. A person who completed sign-in inside that window but is no longer allowed at fill time is not included. When hosted admission is on, a person is allowed when their user login is listed or an organisation login saved from their last completed sign-in is on the organisation list as it stands when the queue is filled for that occasion. The product does not ask GitHub again only to check membership. When hosted admission is off, the lists do not refuse anyone, and the set is still only people who signed in inside the window and are not waiting after invalid stored access. The scheduled collection uses its own worker credential for that operator. That credential is a second GitHub refresh token stored during the same hosted sign-in, and it is not the refresh token that keeps the browser signed in. The auth cookie keeps a different refresh token. A completed sign-in that stores a worker refresh token replaces any previous one. A completed sign-in that does not store a worker refresh token leaves the scheduled collection with no worker refresh token it can renew. While that person stays signed in, storing a replacement worker refresh token ends a stored-access wait, does not move the 30-day window, does not replace the saved organisation list, and does not start a scan. The Repositories page asks them to choose a refresh of only that token as soon as it is missing, or as soon as an overnight scan has failed because it cannot be used. Choosing it sends them through GitHub authorisation again and stores only the worker token from that authorisation. It does not refresh the browser token. Cancelling, or a refresh that does not store a worker token, leaves them signed in and does not record a scan failure. The ask is on that page only. The overnight scan may renew only that worker token. Renewing it does not sign the operator out and does not send them through GitHub sign-in again while that browser session is still valid. The person does not need to be signed in, on the Repositories page, or watching the screen. The operator-facing app does not have to be running. A scheduled collection process, separate from that app, fills the queue at each occasion and processes it. This specification does not name the host, project, or wiring of that process. ### User Story 6 - Keep the last success when the overnight run does not finish cleanly (Priority: P2)

A daily collection that fails uses the same short reasons the operator already understands: a sign-in or token problem, a GitHub rate limit, or an unexpected error. The previous successful snapshot stays as it was, and its finish time stays visible beside the failed run. If the scheduled collection process stops while a pass of a daily collection is running, the next visit is told `stalled` once no liveness mark has been recorded for more than 5 minutes, while the stored status stays `running`. That report does not say that the operator-facing app stopped. The operator-facing app stopping, or not running, does not by itself change that stored status and does not miss the day. That pass does not rejoin the queue. People still waiting on today's queue, including a further try waiting at the back, are not interrupted by that stop. That queued work is still taken as soon as possible after the scheduled collection process is back, and it runs only when that person is still allowed. If stored access cannot be used, the run fails with the sign-in or token reason, further tries stop, and later scheduled collections wait until the worker refresh token is stored again. The operator can start a collection themselves, using the start control they already have, once they are not queued and no collection for them is in progress. A reported `stalled` scan is not in progress. The operator may start a collection by hand, which sets `running` and updates the liveness mark. This feature does not add a retry control.

Access the operator already granted is what the daily collection uses. If that stored access cannot be used, the run fails at once with the sign-in or token reason. It is not tried again as part of that occasion. After that failure, no further daily collection starts until the worker refresh token is stored again. A completed sign-in that stores only the browser refresh token restarts the 30-day window and does not lift the wait. A worker-token refresh while they stay signed in is a second GitHub authorisation that stores only that token, lifts the wait, does not refresh the browser token, does not move the 30-day window, does not replace the saved organisation list, and does not start a scan.

A GitHub rate limit or an unexpected error is treated as a problem that may pass quickly. The same daily collection is tried again up to 3 times. Each further try goes to the back of the queue and must not start until a minimum wall-clock wait has elapsed. For a rate-limit failure, that wait is at least the GitHub-indicated retry period when the product already has one from that failure, otherwise at least 2 minutes. For an unexpected error, each further try waits at least a staggered minimum measured from that failed attempt: 3 minutes before the first further try, 6 minutes before the second, 12 minutes before the third. Queue position alone is not enough when this account is alone in the queue. The further try still does not hold the queue up for other accounts: anyone already ahead runs first, and the minimum wait still applies before the further try may start. Those further tries are part of the same run, not a new occasion and not a list of attempts. While a further try waits at the back, the page shows the stored status as scheduled. It does not show the run as failed, and it does not list the tries. If one of them succeeds, that success is the run and the remaining tries do not happen. If they all fail, the page shows one short reason and when that run failed, together with the finish time of the latest successful snapshot when one exists. That failure does not stop the next eligible day, and it does not move the 30-day window. A stop or crash during a taken pass is not one of these further tries. The stored status stays `running`. Once no liveness mark has been recorded for more than 5 minutes, the page is told `stalled`, not `running`. That report does not rejoin the queue. A later fill may queue that stalled account when the other eligibility rules allow, which sets the stored status to `scheduled`. A further try already waiting at the back is queued work, not a stalled scan, and it is still taken after the scheduled collection process is back. It runs only when that person is still allowed. If stored access cannot be used, the run fails with the sign-in or token reason, further tries stop, and later scheduled collections wait until the worker refresh token is stored again. The page shows that waiting further try as `scheduled`. A stop during that wait is not reported as `stalled`.

**Why this priority**: An overnight failure must not wipe the snapshot later features already rely on. A brief problem calling GitHub should not be the result the operator sees the next morning. The operator should see the same kind of outcome they see when a collection they started does not finish, and should still see when the last successful collection finished. Repeating a daily collection that the stored access cannot support would keep failing without the operator present.

**Independent Test**: Keep a successful snapshot. Cause a rate limit or an unexpected error on the daily collection and confirm the same run is tried again up to 3 times by going to the back of the queue and waiting the required minimum before each further try. While that further try waits, confirm the page shows the stored status as scheduled, not as running or finished, and does not list the tries. With only one eligible account queued, confirm the next try does not start immediately after the failure (and for unexpected errors confirm staggered waits of 3, 6, and 12 minutes between further tries). With another account already queued, confirm that other account runs before the retry and that the minimum wait still applies before the further try starts. Confirm a try that then succeeds becomes the kept snapshot, and confirm that when every try fails the page shows one reason, when the run failed, and the unchanged earlier finish time. Cause a sign-in or token failure and confirm there is no further try that occasion, and that the following 05:00 UTC starts nothing until the worker refresh token is stored again. Confirm the next eligible day still starts after a rate limit or an unexpected error that has finished. Confirm a scan reported as `stalled` is queued again by a later fill when the other eligibility rules allow, and that the new entry sets the stored status to `scheduled`. Confirm the page has no retry control, and that the existing start control can start a collection while the account is reported `stalled`. Separately, stop the scheduled collection process during a daily run and, once no liveness mark has been recorded for more than 5 minutes, confirm the next visit is told `stalled` and the stored status is still `running`, and the queue entry has not rejoined. Stop the scheduled collection process while a further try is only waiting at the back of the queue and confirm that queued work still runs and is not reported as `stalled`.

**Acceptance Scenarios**:

1. **Given** a successful snapshot exists, **When** a later daily collection fails, **Then** the page shows the FR-025 text for that finished failure, including when it failed and one short reason (a sign-in or token problem, a GitHub rate limit, or an unexpected error), and it still shows the finish time of that successful snapshot. ### User Story 7 - Run the fill whenever it is asked, and follow recent sign-ins (Priority: P2)

Under the current schedule, if the scheduled collection process is running at 05:00:00 UTC, that request runs the fill then. Whether the operator-facing app is running does not decide that. If the process is not running at 05:00:00 UTC, it runs the same fill when it is running again, including after 05:15:00 UTC. A fill at any time queues every eligible person who is not already queued or in progress, including someone whose scan already succeeded earlier that day. There is no extra wait after a finished scan, and the clock is not a reason to refuse the fill. The product does not add a second queue entry for someone who is already queued or whose scan is in progress. Work already on the queue is taken whenever the process takes the next entry, at any time of day, including a further try waiting at the back. That scan is attempted when the person is still allowed, including when their latest completed sign-in is older than 30 days because the message waited. If stored access cannot be used, the run fails with the sign-in or token reason, further tries stop, and later scheduled collections wait until the worker refresh token is stored again. If they are no longer allowed, that queued scan does not run: the queue entry is removed, the stored status is suspended with `suspensionReason` `notAllowed`, and the last scan time, result, and result comment are not overwritten because no scan ran, the next person is taken, and the page states that no scheduled collection will run, and why. A pass that was running when the worker stopped or crashed is left stored as `running`. Once no liveness mark has been recorded for more than 5 minutes, callers are told `stalled`, not `running`. The earlier queue entry does not rejoin because the mark lapsed. A reported `stalled` account does not count as in progress. A later fill queues that account when the other eligibility rules allow, and that new queue entry sets the stored status to `scheduled`. The operator may start a collection by hand while the account is reported `stalled`. That hand-started collection sets `running` and updates the liveness mark. The earlier queue entry does not rejoin. A further try that was only waiting stays shown as `scheduled` and still runs. The next time this delivery asks is the following day at 05:00 UTC. That is the next planned ask, not a refusal of a fill that runs sooner. Completing sign-in does not itself start a scan. A person who completes sign-in is included in the next fill when they are eligible and not already queued or in progress, including after an earlier success, and they can still start a collection by hand.

A scheduled collection needs both a recent sign-in and current permission to use the product. The allow lists are not the list of people who are scanned. A person who is allowed but has never completed a hosted sign-in does not get a scheduled collection. A person who was allowed, and who signed in inside the last 30 days, does not get one after they are no longer allowed. Removing a user login stops that person's daily collection. Removing an organisation login stops the daily collection for people whose saved sign-in organisations allowed them only through that organisation. A person who remains allowed by their own user login still receives one while their sign-in is inside 30 days and they are not waiting after invalid stored access. Membership is not refreshed from GitHub at queue fill for that occasion. Turning admission on with empty lists stops every daily collection. Turning admission off does not scan people who have not signed in. It stops the lists from refusing people who have signed in inside the window.

A completed sign-in starts or restarts that person's 30-day window from that sign-in. Storing the browser refresh token completes that sign-in even when the worker refresh token is not stored. Signing in does not itself start a collection. A sign-in that does not complete does not start the window and does not lift a wait after invalid stored access. A completed sign-in lifts a wait after invalid stored access only when it stores the worker refresh token. A worker-token refresh while they stay signed in also lifts that wait when it stores the worker refresh token, and does not move the 30-day window or the saved organisation list, and does not start a scan. Until the worker refresh token is stored again, the next overnight scan fails with the sign-in or token reason when they are not already in that wait. A completed sign-in does not put a person into the daily set while they are not allowed.

**Why this priority**: A GitHub outage or a process that was down at 05:00 UTC must not mean the operator is told the scans cannot be run because the clock has passed 05:15 UTC. The normal ask is still once a day. A fill that is run at another time uses the same rules. Scanning everyone on an allow list would collect for accounts that have never signed in. Continuing to collect after someone loses access would collect for a person the product no longer lets in.

**Independent Test**: Make the scheduled collection process unavailable at 05:00 UTC, bring it back later the same UTC day, including after 05:15 UTC, and confirm eligible people are queued then and each queued request runs when it is picked up. Separately, run the fill again after a scan has succeeded and confirm that person is queued again once they are not queued or in progress. Have a person complete sign-in and confirm that sign-in alone does not start a scan, while a later fill includes them when they are eligible, and a hand-started collection still works. Remove a person who signed in inside 30 days from admission and confirm the next fill does not queue them. Put a person who has never signed in onto an admission list and confirm no unattended collection starts for them.

**Acceptance Scenarios**:

Work already queued still runs when that person is still allowed. The operator-facing app being up does not by itself fill the queue, and it being down does not cancel a fill the process can still do.

### User Story 8 - Read the real scan status at any time (Priority: P1)

In hosted sign-in, the operator can open the Repositories page at any time of day or night and see the current state of scanning for their account. The page, and any other process that asks, receives the reported status and the human-friendly text in FR-025. It does not guess running, finished, failed, or suspended from the clock, from whether they had the page open, or from whether a worker seems to be missing. When a hosted sign-in record exists and the status blob is absent, the page reports `never run` with the FR-025 text, and that read does not create the blob.

The product keeps that record for each account it has seen under the same logged-in-within-the-last-30-days rule the daily fill already uses. The record is created when the account is first recorded for later scanning, including when the access the scanner will use is stored. The default status is `never run`, with an empty last-run time, an empty result, and an empty comment. A later sign-in does not put a record back to `never run`.

The record holds the status, the date and time the last scan was run, the result of that last run, a result comment, and `suspensionReason` (`notAllowed` or empty). The result is success, failure, or empty. The comment is Success when the last run succeeded, the failure detail when it failed, and empty when no scan has run. The status is `never run`, `scheduled`, `running`, `finished`, or `suspended`, as defined in the 2026-11-25 clarification. The product may store a further status only when that state is real and the page or another process cannot tell the truth without it.

`scheduled` is set when a queue entry is created and is waiting, including a further try sent to the back of the queue. `running` is set when the worker takes that entry. `finished` is set when the worker finishes it: result success and comment Success, or result failure and a comment that states why. While further tries remain, the status goes back to `scheduled` when the entry is waiting again. The page does not show `finished` or a failed result for that run until the try sequence has ended. `suspended` is set when the worker takes the entry and cannot leave a scan that is allowed to run again yet. If the account is no longer allowed, the scan does not run, the last run time, result, and result comment are left as they were, and `suspensionReason` is `notAllowed`. The page shows the fixed comment that they are not allowed. If stored access cannot be used, the token exchange fails before the catalogue walk: the result is failure, the comment states the sign-in or token problem, and `suspensionReason` stays empty. When no newer worker refresh token is already stored, the status is `suspended` and later scheduled collections still wait until the worker refresh token is stored again. When a newer worker refresh token is already stored, the status is `finished`, the failure stays visible, and the wait is not set. A queued scan that has not been taken uses the worker token stored when the worker takes it. A scan already running keeps the token it started with. When GitHub issues a replacement for that token, the scan does not write it over a newer worker token already stored. The newer token stays stored. The scan may store a replacement only while the token it started with is still the stored worker token.

A hand-started collection in hosted sign-in updates the same record: `running` when that scan starts, and `finished` or `suspended` when it ends, with the same result and comment rules. The daily fill does not change. It still queues from its own rules, and it treats `scheduled` and `running` as already queued or in progress.

The worker that takes queue entries must leave the stored status in agreement with reality. While it is scanning an account whose stored status is `running`, and that scan is still working, it records a fresh liveness mark at least once every 60 seconds until that scan records `finished` or `suspended`. The same duty applies to a hand-started hosted scan. If no liveness mark has been recorded for more than 5 minutes, every process that asks for that account's scan status is told `stalled`, not `running`. The stored status stays `running` until a new scan is queued or started by hand. A reported `stalled` account does not count as in progress. A later fill queues that account when the other eligibility rules allow, and that new queue entry sets the stored status to `scheduled`. The operator may start a collection by hand while the account is reported `stalled`. That hand-started collection sets `running` and updates the liveness mark. The earlier queue entry does not rejoin. If a fill, another copy of the scheduled collection process, and that hand start all try while the account is reported `stalled`, only one new scan starts. The first to set `scheduled` or a new `running` wins. Every other attempt does not start a second scan and does not change the stored status, the liveness mark, or the snapshot.

In the lean local posture there is still no scheduled worker and no scheduled status. A collection the operator starts there stays the on-demand collection they already have.

**Why this priority**: If the page says a scan is running when the worker has stopped updating, the operator is told the wrong state. The operator also needs the truth in the middle of the night, not only just after 05:00 UTC.

**Independent Test**: Complete a hosted sign-in for a new account and confirm the stored status is `never run`, with empty last-run time, result, and comment, before any queue entry exists. Run a fill and confirm the status is `scheduled` while the entry waits, including at a time that is not 05:00 UTC. When the worker takes the entry, confirm `running`. When the scan succeeds, confirm `finished`, result success, comment Success, and the finish time. When stored access cannot be used, confirm `suspended`, result failure, and the sign-in or token comment, and confirm a later fill does not queue them until the worker refresh token is stored again. When the worker takes an entry for an account that is no longer allowed, confirm the scan does not run, the status is `suspended`, `suspensionReason` is `notAllowed`, the previous last-run time, result, and result comment are unchanged, and the earlier successful snapshot is unchanged. Stop or crash the worker after status is `running` and before a normal finish, then confirm the stored status stays `running`, and once no liveness mark has been recorded for more than 5 minutes callers are told `stalled`, not `running`, and confirm a later fill queues that account when the other eligibility rules allow and sets the stored status to `scheduled`.

**Acceptance Scenarios**:

1. **Given** a hosted account is recorded for later scanning and no scan has run, **When** the operator views the Repositories page at any time of day, **Then** the status is `never run` and the last-run time, result, and comment are empty.
2. **Given** a fill has queued that account and the worker has not taken the entry, **When** the operator views the page, including hours before or after 05:00 UTC, **Then** the status is `scheduled`. The page does not show `running`.
3. **Given** the worker has taken the queue entry and has not finished it, **When** the operator views the page, **Then** the status is `running`, and the page uses the FR-025 running sentence, which does not say who started it.
4. **Given** the worker finishes a scan successfully, **When** the operator views the page, **Then** the status is `finished`, the result is success, the comment is Success, and the page shows when that scan finished and the snapshot count.
5. **Given** the worker takes an entry and the account is no longer allowed, **When** that pickup is dealt with, **Then** the scan does not run, the status is `suspended` with `suspensionReason` `notAllowed`, the last scan time, result, and result comment are unchanged, the earlier successful snapshot is unchanged, and the next queued account is taken.
6. **Given** the worker attempts a scan and the stored access cannot be used, and no newer worker refresh token is already stored, **When** that attempt ends, **Then** the status is `suspended`, the result is failure, the comment states the sign-in or token problem, further tries do not start, and later fills do not queue them until the worker refresh token is stored again. **Given** that scan was already running on an older worker token and a newer worker refresh token is already stored, **When** that attempt fails because the older token cannot be used, **Then** the status is `finished`, the result is failure, the comment states the sign-in or token problem, the wait is not set, and further tries do not start.
7. **Given** a rate-limit or unexpected-error further try is waiting at the back of the queue, **When** the operator views the page, **Then** the status is `scheduled`, not `running` and not `finished`. The tries are not listed.
8. **Given** the worker has set `running` for an account, **When** the worker crashes or is stopped before it records a normal finish, **Then** the stored status stays `running`, and once no liveness mark has been recorded for more than 5 minutes callers are told `stalled`. **Given** that same pass records a real success or failure before a newer scan is queued or started, **Then** the stored status becomes `finished` with that real result, and a success replaces the snapshot. **Given** a newer scan is queued or started first, **Then** that earlier pass does not change the stored status, the liveness mark, or the snapshot. A later fill queues a still-stalled account when the other eligibility rules allow and sets the stored status to `scheduled`. The operator may also start a collection by hand, which sets `running` and updates the liveness mark.
9. **Given** the operator starts a collection by hand in hosted sign-in while they are not `scheduled` and not reported `running`, including when they are reported `stalled`, **When** that scan starts and later succeeds, **Then** the same record moves to `running` and then to `finished` with result success and comment Success.
10. **Given** the stored status is `scheduled` and the account has no queue entry at all, **When** the next live scheduled collection process runs a fill, **Then** an empty last result sets the status to `never run`, any other last result sets it to `finished`, the last scan time, result, and comment are unchanged, and no failure comment is added. If the other eligibility rules allow, that same fill queues the account and sets `scheduled`. **Given** a further try exists but is not yet visible, **When** that process runs, **Then** the status stays `scheduled` and a second entry is not added.
11. **Given** the lean local posture, **When** the operator views collection, **Then** the page does not show a scheduled account status from a worker, and no scan starts because of the clock.
12. **Given** a hosted scan is still working, whether the queue worker or a hand-started collection is doing it, **When** that work continues for longer than 5 minutes and a fresh liveness mark is recorded at least once every 60 seconds until the scan records `finished` or `suspended`, **Then** callers are told `running`, not `stalled`.
13. **Given** an account is reported `stalled`, **When** a scheduled fill, another copy of the scheduled collection process, and the operator's start control all try to collect at the same moment, **Then** exactly one new scan starts. The first attempt to set `scheduled` or a new `running` wins. Every other attempt does not start a second scan and does not change the stored status, the liveness mark, or the snapshot. The page shows that one scan.

### Edge Cases

The cookie keeps the refresh token from the first authorisation, and storing the worker token leaves that browser token usable and unchanged. The product keeps that worker token only when the browser refresh token still works afterwards. When it does not, the product discards that worker token and sends them through GitHub again on the existing GitHub App to restore the browser token. Sign-in is complete once that restored browser token works. The worker token stays missing until a later authorisation stores one without leaving the browser token unusable. That restore does not store a worker token and does not change a 30-day window or organisation list already saved for that sign-in. The same check applies to a worker-token authorisation from the Repositories page: a broken browser token is restored, the new worker token is not kept, and the 30-day window, saved organisation list, and stored-access wait stay as they were. Cancelling the second authorisation, or storing no worker token, leaves the sign-in complete. A completed sign-in that stores a worker refresh token replaces any previous one. A completed sign-in that does not store a worker refresh token leaves the scheduled collection with no worker refresh token it can renew. While that person stays signed in, storing a replacement worker refresh token ends a stored-access wait, does not move the 30-day window, does not replace the saved organisation list, and does not start a scan. The Repositories page asks them to choose a refresh of only that token as soon as it is missing, or as soon as an overnight scan has failed because it cannot be used. Choosing it sends them through GitHub authorisation again and stores only the worker token from that authorisation. It does not refresh the browser token. Cancelling, or a refresh that does not store a worker token, leaves them signed in and does not record a scan failure. The ask is on that page only. The overnight scan may renew only that worker token. Renewing or replacing it does not clear the cookie, does not invalidate it, and does not require the operator to sign in with GitHub again while the cookie is still valid. The worker does not exchange that session refresh token and does not store a rotated replacement of it. If the worker credential cannot be used, the run fails with the sign-in or token reason. That failure is not repaired by spending the browser refresh token.

Until a newer scan for that account is queued or started by hand, the pass that was scanning may record its real success or failure, including after callers have been told `stalled`. If that pass updates the liveness mark before a newer scan starts, callers are told `running` again. A success sets `finished`, result success, and comment Success, and replaces the snapshot as any other success does. A failure sets `finished` with the real failure result and comment. Callers are then told that finished status. Once a newer scan has set the stored status to `scheduled` or to a new `running`, that earlier pass must not change the stored status, the liveness mark, or the snapshot. A later fill queues that account when the other eligibility rules allow, and that new queue entry sets the stored status to `scheduled`. The operator may start a collection by hand while the account is reported `stalled`. That hand-started collection sets `running` and updates the liveness mark. The earlier queue entry does not rejoin. When a fill, another copy of the scheduled collection process, and a hand-started collection all try while the account is reported `stalled`, exactly one new scan starts. The first to set `scheduled` or a new `running` wins. Every other attempt does not start a second scan and does not change the stored status, the liveness mark, or the snapshot.
- The daily collection and a collection the operator starts are the same collection. There is one current snapshot per operator. A newer success replaces the older one, whichever way the run started.
- If the stored status is `scheduled` and the account has no queue entry at all, the next live scheduled collection process restores the status from the last result before it decides who to queue. An empty last result sets `never run`. Any other last result sets `finished`. The last scan time, result, and comment stay as they were, and no failure comment is added. The same fill may queue the account under the existing rules. An entry that exists but is not yet visible, including a further try waiting for its minimum delay, still counts, and the status stays `scheduled`.
- A daily run that is still in progress at the next 05:00 UTC, or still waiting on the previous occasion's queue, does not gain a second queue entry.
- An account with no linked repositories can still have a successful daily snapshot: success, a finish time, and a count of zero. That is different from never having run, and different from a failed first run.
- Leaving the Repositories page, being signed out, or the operator-facing app stopping or not running does not by itself mark a daily run as interrupted. A worker stop or crash during a taken scan means the stored status stays `running`, and once no liveness mark has been recorded for more than 5 minutes callers are told `stalled`, not `running`. The stored status stays `running`. Waiting on today's queue before the worker has taken the entry is shown as scheduled, not as running. A further try waiting at the back is shown as scheduled, and a stop during that wait does not interrupt the run. That queued work is still taken as soon as possible after the scheduled collection process is back, and it runs only when that person is still allowed. If stored access cannot be used, the run fails with the sign-in or token reason, further tries stop, and later scheduled collections wait until the worker refresh token is stored again.
- The live catalogue can change after a snapshot is taken. The snapshot stays as last collected until a later collection succeeds. Reloading the live catalogue does not change the snapshot and does not start a collection.
- Repositories the Repositories page cannot already show for that operator are not added by the daily collection. Organisation-owned repositories appear only when they are already part of that personal catalogue.
- One operator's scheduled run does not count as another operator's in-progress run. Eligible people are queued at the same scheduled occasion fill. Only one scheduled collection runs at a time. A later start, at any time the process runs, is still that occasion's queued work. The operator does not see the queue or their place in it.
- More than one running copy of the scheduled collection process does not queue or collect an eligible person twice for the same occasion. Copies of the operator-facing app do not run the daily collection. The single snapshot is still written once.
- The Repositories page shows collection status and does not list the repositories inside the snapshot. The live catalogue remains the list on that page.
- The product does not keep a log of past daily occasions or past runs. A skipped occasion is not listed on its own.
- When more than one reason means no scheduled collection will run, the page uses one schedule sentence from FR-025, in this order: they are not allowed; otherwise a stored-access wait until they refresh the access used for the overnight collection; otherwise a closed 30-day window until they sign in again. When a stored-access wait is set, that failed run stays visible even if the schedule sentence says they are not allowed.
- The stated fill clock time does not move to the operator's local zone. For the initial default, every hosted operator who will be queued reads the same human-friendly sentence: the next collection runs overnight. The page does not name 05:00 UTC. It does not use a standing sentence that a collection runs each day when this operator will not have one. Processing that queue is not limited to that hour. The 30-day sign-in window is not re-checked when a queued entry is taken. A queued scan does not run when, at the moment the queue reaches it, the person is not allowed to use the product. The queue entry is removed, the stored status is suspended with `suspensionReason` `notAllowed`, and the last scan time, result, and result comment are not overwritten because no scan ran, and the next queued person is taken. The page states that no scheduled collection will run because they are not allowed. It shows suspended and the fixed comment for `suspensionReason` `notAllowed`, and it does not show the scan as running or as a failed snapshot. If stored access cannot be used, the run fails with the sign-in or token reason, further tries stop, and later scheduled collections wait until the worker refresh token is stored again. That failed run stays visible. Those checks are not the fill schedule.
- A personal deployment that remains in the lean local posture does not gain the daily collection because it is running somewhere other than the operator's desk.
- Being allowed does not by itself add a person who has never completed a hosted sign-in. Losing permission removes a person even when their latest completed sign-in is inside 30 days. When admission is off, the lists do not refuse anyone who has signed in inside the window.
- Organisation membership for a scheduled occasion is the set of organisation logins saved from that person's last completed hosted sign-in. Those logins are compared with the organisation allow list as it stands when the queue is filled for that occasion. The product does not ask GitHub again only to check membership. Leaving or joining a GitHub organisation does not change that saved set until the next completed sign-in.
- A completed hosted sign-in sets the 30-day window. It does not cause a collection while the person is not allowed. A sign-in that does not complete does not count.
- A successful collection does not extend the 30 days. Only a completed sign-in does.
- After a daily collection fails because the stored access cannot be used, later daily occasions skip that person until the worker refresh token is stored again. A rate limit, an unexpected error, a reported `stalled` scan, a missed day, or a run already in progress does not cause that skip.
- A rate limit or an unexpected error on a daily collection is tried again up to 3 times, as part of the same run. Each further try goes to the back of the queue and must wait at least the applicable minimum wall-clock delay (GitHub-indicated retry period when the product has one from a rate-limit failure, otherwise 2 minutes; unexpected-error failures use staggered minimums of 3, 6, then 12 minutes before the first, second, and third further tries) before it may start, including when this account is alone in the queue. Other accounts already ahead still run first. A sign-in or token failure is not tried again and does not rejoin the queue. The worker stopping or crashing while a pass is running leaves the stored status `running`. Once no liveness mark has been recorded for more than 5 minutes, callers are told `stalled`. That report is not one of those further tries, it does not change the stored status, and that pass does not rejoin the queue. The page shows a further try waiting at the back as scheduled. A further try already waiting at the back is still taken after the scheduled collection process is back, and it runs only when that person is still allowed. If stored access cannot be used, the run fails with the sign-in or token reason, further tries stop, and later scheduled collections wait until the worker refresh token is stored again.
- The operator does not see a separate entry for each try. While a further try waits at the back, the page shows the stored status as scheduled, not as finished or failed. A failed daily run shows one reason and when it failed, beside the finish time of the latest successful snapshot when one exists.
- This feature does not add a retry control. Collecting again by hand uses the start control the operator snapshot collection already provides. Those hand-started runs are not given the 3 further tries. While an operator is queued for the current occasion, or a collection for them is in progress, that start control does not start a collection. They wait for the queue.

## Requirements *(mandatory)*

### Functional Requirements

**Requirement layering**: **FR-001** is the canonical statement for fill eligibility, catch-up when the process was down at 05:00 UTC, queue processing at dequeue, and concurrency at fill. **FR-021** is the canonical fill-clock versus queue-processing split. **FR-015** states catch-up, sooner fill after technical failure, and hand-start deltas only where they extend FR-001. **FR-017** states admission and the 30-day window at fill; dequeue behaviour follows FR-001 and FR-021. **FR-022** is the canonical stored account scan status. **FR-023** is the canonical rule for the liveness mark and the reported `stalled` status. **FR-024** is the canonical split between the interactive session and the worker credential, including a worker-token refresh while the operator stays signed in. Where FR-001, FR-006, FR-012, FR-020, or FR-021 describe what the page shows for a waiting, running, refused, or stopped scan, FR-022 and FR-023 win. Where earlier text treats the stored access for a scheduled scan as the same refresh token that keeps the browser signed in, FR-024 wins. Where earlier text says a stored-access wait ends only when they complete sign-in again, FR-013 and FR-024 win: storing the worker refresh token again ends that wait, including a worker-token refresh while they stay signed in, and that refresh does not move the 30-day window or the saved organisation list and does not start a scan. Where earlier text says every failure because stored access cannot be used sets `suspended` and the wait, FR-013 wins when a newer worker refresh token is already stored: that failure is `finished`, it stays visible, and the wait is not set. **FR-025** is the canonical human-friendly text for the current scan status and for whether a scheduled collection will run. Where earlier text tells the page or another caller to name 05:00 UTC, tonight, today, the following day, or the daily occasion in that text, FR-025 wins for those words. 05:00 UTC remains when this delivery asks for a fill.

- **FR-001**: In hosted sign-in, each daily fill MUST place a collection on the scheduled scan queue for each person who, at that fill, has a latest completed hosted sign-in no older than 30 days, is currently allowed to use the product, is not waiting after a scheduled collection failed because the stored access could not be used, and is not already queued or in progress. A reported `stalled` account MUST NOT count as queued or in progress. Before that fill decision, the process MUST restore accounts as FR-022 requires when the stored status is `scheduled` and the account has no queue entry at all. A scan that already succeeded earlier that day MUST NOT exclude them. The current schedule asks once per UTC calendar day at 05:00 UTC. That is how often this delivery asks. It MUST NOT be a time window that refuses a fill, and it MUST NOT impose an extra wait after a previous fill or a finished scan. A fill at any time MUST use these same rules. If the scheduled collection process is running at 05:00:00 UTC, the queue MUST be filled then. If it is not, the same fill MUST run when the process is running again, including after 05:15:00 UTC. Those clock times govern when this delivery normally asks. They MUST NOT block processing of an entry already on the queue. More than one copy of the process at the same fill MUST NOT queue the same person twice while they are already queued or in progress. The scheduled collection process MUST run one scheduled collection at a time across those copies. The operator-facing app MUST NOT have to be running for fill or processing. Each queued collection MUST be taken when the queue reaches that person, as soon as the process can take the next entry, without regard to time of day or how long the message has waited. The worker MUST attempt that scan unless that person is not currently allowed to use the product. The 30-day sign-in window MUST NOT be re-checked at dequeue. If the person is no longer allowed, that queued scan MUST NOT run: the product MUST remove that queue entry, MUST set the stored status to suspended with `suspensionReason` `notAllowed`, and MUST NOT overwrite the last scan time, result, or result comment, because no scan ran, and MUST continue with the next queued person. The Repositories page MUST state that no scheduled collection will run, and why, and MUST show suspended and the fixed comment for `suspensionReason` `notAllowed`, and MUST NOT show the scan as running or as a failed snapshot. Any earlier successful snapshot MUST stay unchanged. If stored access cannot be used, the run MUST fail with the sign-in or token reason, further tries MUST stop, later scheduled collections MUST wait until the worker refresh token is stored again, and that failed run MUST stay visible. It MUST NOT have to be in progress at the fill instant. That queue MUST NOT depend on the person opening the Repositories page or choosing the start control. It MUST NOT include a person who is allowed but has never completed a hosted sign-in, or a person who is no longer allowed at fill time.
- **FR-002**: The operator MUST NOT need to be signed in, using the product, or have the operator-facing app running for that daily collection to start and to finish. In hosted sign-in a scheduled collection process, which is not the operator-facing app, MUST queue and run the daily collection. The operator-facing app being down or stopping MUST NOT miss the day and MUST NOT interrupt a daily pass. This specification does not name the host, project, or wiring of that process. The lean local posture has no scheduled collection process.
- **FR-003**: A successful daily collection MUST be the same snapshot a successful hand-started collection would keep for that operator, including the same repository facts the operator snapshot collection already records. It MUST replace the previous successful snapshot. It MUST NOT create a second snapshot or a second kind of collection.
- **FR-004**: The operator MUST still be able to start a collection from the Repositories page in hosted sign-in and in the lean local posture, except while a collection for that operator is already in progress or they are already waiting on the current day's queue. A reported `stalled` account is not in progress for this rule. That control MUST remain separate from reloading the live catalogue.
- **FR-005**: In the lean local posture, including a personal deployment that stays in that posture, there MUST NOT be a scheduled collection process, and the product MUST NOT start a collection on a schedule, including at 05:00 UTC. The product MUST explain that nothing collects on a schedule, and that the snapshot is kept on this machine rather than promised on another machine. The operator MUST be able to collect when they ask, without being asked to add infrastructure.
- **FR-006**: In hosted sign-in, the Repositories page MUST state the real next scheduled collection for that operator, including when no collection has ever run. When the next ask will queue a collection for them, the human-friendly text MUST be the overnight sentence in FR-025. While they are still waiting in that day's queue and the collection has not started, that text MUST stay the overnight sentence, MUST NOT describe the day as missed, MUST use the FR-025 text for `scheduled`, and MUST NOT use the running text until the worker has taken the entry. When no occasion will queue a collection, the page MUST use one schedule sentence from FR-025 and MUST NOT say that the next collection runs overnight. That sentence MUST say that no scheduled collection will run because you are not allowed to use the product, when that is true. Otherwise, when a stored-access wait is set, it MUST say that no scheduled collection will run until you refresh the access used for the overnight collection. Otherwise, when the 30-day window is closed, it MUST say that no scheduled collection will run until you sign in again. When a stored-access wait is set, the page MUST show that failed run and the sign-in or token reason even when the schedule sentence says they are not allowed. The human-friendly text MUST NOT name 05:00 UTC, tonight, today, or the following day. The page MUST still show when the latest successful collection finished. The current run MUST use the FR-025 status sentence and MUST NOT say who started it. When the operator can still use the product, and they are not queued or in progress, the page MUST show that they can start a collection themselves. While the operator is signed in, the Repositories page MUST ask them to refresh only the worker token as soon as that token is missing, or as soon as an overnight scan has failed because that token cannot be used. The operator MUST choose that refresh. If they cancel, or the refresh does not store a worker token, they MUST stay signed in, the browser session MUST stay unchanged, and that attempt MUST NOT record a scan failure. The ask MUST be on the Repositories page only. It MUST NOT appear on every page, and it MUST NOT be a separate settings page. When the worker token is missing, the operator is otherwise eligible, and the stored-access wait is not set, the human-friendly text MUST still say the next collection runs overnight and the page MUST also ask. When the worker token is present and that failure is not the current block, the page MUST NOT ask. The lean local posture MUST NOT show this ask.
- **FR-007**: This feature MUST NOT offer a control or a settings page to change the time, how often the collection runs, or the 30 days. It MUST NOT add a retry control. After a daily collection fails, the operator collects again by hand only through the start control the operator snapshot collection already provides. The worker-token refresh in FR-024 is chosen on the Repositories page. It is not that settings page, and it is not a retry control for a failed scan.
- **FR-008**: The product MUST allow only one in-progress collection per operator, and only one scheduled collection at a time across operators and across running copies of the scheduled collection process. A reported `stalled` account MUST NOT count as that in-progress collection. When more than one attempt would start a new scan while that account is reported `stalled`, including a fill, another copy of the scheduled collection process, and a hand-started collection, exactly one new scan MUST start. The first attempt to set `scheduled` or a new `running` wins. Every other attempt MUST NOT start a second scan, MUST NOT add a second queue entry, and MUST NOT change the stored status, the liveness mark, or the snapshot. If a collection for that operator is already in progress when the queue would be filled for that occasion, or they are already waiting on the previous occasion's queue, that fill MUST NOT add another entry. If a scheduled collection is in progress for that operator, or they are waiting on the current occasion's queue, including at the back of the queue for a further try, the start control MUST NOT start another.
- **FR-009**: The human-friendly text for the current run MUST use the sentences in FR-025. It MUST NOT say who started that run. It MUST NOT call that run the daily occasion.
- **FR-010**: Opening the Repositories page, or reloading the live catalogue, MUST NOT start a collection. The daily occasion in hosted sign-in is the only new way a collection starts.
- **FR-011**: While a daily collection is in progress, the operator MUST be able to keep using the rest of the product. If they stay on the Repositories page, the state, the start time, and the recorded count MUST update without them leaving or reloading.
- **FR-012**: A daily collection that fails MUST follow the operator snapshot collection: the same three short failure reasons, the previous successful snapshot unchanged, and in-progress recordings not presented as a new successful snapshot. A worker stop or crash while a pass is running MUST follow FR-023. A reported `stalled` scan MUST NOT state that the operator-facing app stopped and MUST NOT use the three short failure reasons. The operator-facing app stopping MUST NOT by itself change that stored status. That in-progress pass MUST NOT rejoin the queue. A stop while the person is only waiting on the queue, including for a further try, MUST NOT report that run as `stalled`. The human-friendly text MUST still say that the overnight collection started that run, as FR-025 requires. When a successful snapshot exists, the page MUST show its finish time together with the failed run or the reported `stalled` scan.
- **FR-013**: The daily collection MUST use the worker credential in FR-024, which is access that operator already granted. If that worker credential cannot be used, the run MUST fail at once with the sign-in or token reason, MUST NOT try that occasion again, and MUST NOT publish a new successful snapshot. It MUST NOT repair that failure by exchanging the interactive session's refresh token. After that failure, the product MUST NOT start further daily collections for that person until the worker refresh token is stored again. A completed sign-in that stores the browser refresh token and does not store the worker refresh token MUST restart the 30-day window and MUST NOT lift that wait. When the worker refresh token is absent and the person is not already in that wait, the next overnight scan MUST fail with the sign-in or token reason. A completed sign-in that stores the worker refresh token MUST lift the wait and restart the 30-day window from that sign-in. A worker-token refresh while the operator stays signed in MUST store a replacement worker refresh token, MUST lift that wait, MUST NOT move the 30-day window, MUST NOT replace the saved organisation list, and MUST NOT start a scan. A scheduled scan that is queued and not yet taken MUST use the worker refresh token stored at the moment the worker takes it. A scheduled scan that is already running MUST keep the worker token it started with, and that refresh MUST NOT restart it. When GitHub issues a replacement refresh token for the worker token that scan started with, the scan MUST NOT write that replacement over a newer worker refresh token already stored. That newer token MUST stay stored. The scan MAY store a replacement only while the worker token it started with is still the stored worker token. If that running scan then fails because the token it started with cannot be used, and a newer worker refresh token is already stored, the product MUST show that failure, MUST set the stored status to `finished` with result failure and the sign-in or token comment, MUST leave `suspensionReason` empty, MUST NOT set the stored-access wait, and MUST NOT start a further try. A later fill follows the existing eligibility rules. If that failure is recorded and no newer worker refresh token is stored, the status MUST be `suspended` and the wait MUST be set, as before. When a worker-token refresh lifts a stored-access wait and the stored status is `suspended` because stored access could not be used, the product MUST set the status to `finished`, MUST keep that failure result and the sign-in or token comment, and MUST leave `suspensionReason` empty. A later daily collection MUST still require the 30-day window as it stands and that they are currently allowed. A daily collection that fails for a GitHub rate limit or an unexpected error, or that is reported `stalled`, MUST NOT create that wait and MUST NOT move the 30-day window.
- **FR-014**: One operator MUST NOT be able to read another operator's snapshot, collection status, or finish time, whether the run was daily or hand-started.
- **FR-015**: A daily fill MUST be allowed at any time of day. Catch-up when the process was not running at 05:00:00 UTC follows FR-001. The clock MUST NOT refuse a fill, and a finished scan MUST NOT start a waiting period before the next fill. Each fill MUST queue every eligible person who is not already queued or in progress, including someone whose scan already succeeded earlier that day, as in FR-001. A technical failure, including GitHub being unavailable, MUST NOT by itself postpone the next unattended attempt until the following day's 05:00 UTC; this delivery MAY enqueue a sooner fill ask (`unmetFill` in data-model.md). Queue processing, dequeue, interruption, and restart behaviour follow FR-001 and FR-021. The next time this delivery asks is the following day at 05:00 UTC. That planned ask MUST NOT forbid a fill that runs sooner. The operator MUST still be able to start a collection by hand when they can use the product and they are not already queued or in progress.
- **FR-016**: Completing a hosted sign-in MUST NOT itself start a collection. This delivery asks at 05:00 UTC once each UTC day. A fill at any other time uses the same eligibility rules. When they can use the product, they MUST still be able to start a collection by hand at any time. A person inside the 30-day window who is allowed and is not waiting because stored access could not be used MUST be queued at a fill when they are not already queued or in progress, including when they completed sign-in after 05:00 UTC and including when a scan for them already succeeded earlier that day.
- **FR-017**: A scheduled collection MUST require both a completed hosted sign-in inside the last 30 days and current permission to use the product at fill time for that occasion. The allow lists MUST NOT be scanned in full. When admission is on, organisation allowance MUST be decided from the organisation logins saved at that person's last completed hosted sign-in, compared with the organisation allow list as it stands when the queue is filled for that occasion. The product MUST NOT call GitHub only to refresh that membership. A later change of GitHub organisation membership MUST NOT change eligibility until the next completed sign-in saves a new set. A person who is allowed and has never completed sign-in MUST NOT be queued. A person who is no longer allowed MUST NOT be queued, including when their latest completed sign-in is inside 30 days. Removing a user login MUST stop that person from being queued at the next fill. Removing an organisation login MUST stop queueing for a person who was allowed only through that saved organisation, and MUST NOT stop a person who remains allowed by their own user login. When hosted admission is on and both lists are empty, no scheduled fill MUST queue anyone. When hosted admission is off, the lists MUST NOT refuse a person who completed sign-in inside the window, and MUST NOT add a person who has not signed in. Allowing a person again, while their latest completed sign-in is still inside the window and they are not waiting after invalid stored access, MUST include them at the next scheduled fill. Queuing at fill uses the 30-day window, admission, and stored-access checks at fill time (FR-001). When a queued entry is about to run, follow FR-001 and FR-021.
- **FR-021**: Queuing a scheduled scan and running a queued scan MUST be treated as different processes. They MAY use different rules. The scheduled collection process MUST take entries on the scheduled scan queue whenever it is running. Time of day, including the ask at 05:00 UTC, MUST NOT decide whether a fill may run. How often the schedule asks is separate from the fill rules. A fill MUST NOT be refused because a scan already succeeded, because a fill already happened, or because the clock has passed 05:15 UTC. Time of day MUST NOT block an entry already on the queue. The 30-day sign-in window MUST apply only when deciding whether to place someone on the queue at fill time. When an entry is about to run, including a further try at the back, the product MUST attempt the scan unless the person is not currently allowed to use the product. If the person is no longer allowed, it MUST remove that queue entry, MUST set the stored status to suspended with `suspensionReason` `notAllowed`, and MUST NOT overwrite the last scan time, result, or result comment, because no scan ran, and MUST continue with the next queued person. The page MUST state that no scheduled collection will run, and why, and MUST show suspended and the fixed comment for `suspensionReason` `notAllowed`, and MUST NOT show the scan as running or as a failed snapshot. If stored access cannot be used, the run MUST fail with the sign-in or token reason, further tries MUST stop, later scheduled collections MUST wait until the worker refresh token is stored again, and the page MUST show that failed run. Concurrency rules in this feature still apply. The specification MUST remain compatible with a later change to fill frequency or per-operator schedules without rewriting these queue-processing rules.
- **FR-018**: The product MUST NOT keep a log or list of past daily occasions. A skipped occasion is not listed on its own. The operator-facing record is the stored account scan status (current status, last scan time, last result, and result comment), the latest successful snapshot when one exists, and the statement of the next occasion or that no scheduled collection will run. That status is the current truth, not a log of earlier statuses.
- **FR-019**: A completed hosted sign-in MUST set that person's 30-day window from that sign-in, including when that sign-in stores the browser refresh token and does not store the worker refresh token. That window alone MUST NOT cause a daily collection while the person is not allowed. A sign-in that does not complete MUST NOT start or restart the window and MUST NOT lift a wait after invalid stored access. A completed sign-in MUST lift a wait after invalid stored access only when it stores the worker refresh token. A worker-token refresh while the operator stays signed in MUST lift that wait when it stores the worker refresh token, and MUST NOT start or restart the 30-day window or replace the saved organisation list. A successful daily or hand-started collection MUST NOT by itself extend the window. A sign-in exactly 30 days before the occasion is inside the window. A sign-in older than 30 days is outside it.
- **FR-020**: When a daily collection fails because of a GitHub rate limit or an unexpected error, the product MUST try that same run again, up to 3 further tries, by placing that account at the back of the queue. The product MUST NOT start a further try until at least the applicable minimum wall-clock period has elapsed: for a rate-limit failure, at least the GitHub-indicated retry period when the product already has one from that failure, otherwise at least 2 minutes; for an unexpected-error failure, staggered minimum waits measured from that failed attempt: at least 3 minutes before the first further try, at least 6 minutes before the second further try, and at least 12 minutes before the third further try. That minimum MUST apply even when no other account is ahead in the queue. Other accounts already queued ahead MUST run before that further try. The further try MUST NOT hold those other accounts up. A try that succeeds MUST become the kept snapshot and MUST stop the remaining tries. If every try fails, the product MUST record one short reason and the time the run failed, and MUST show that beside the finish time of the latest successful snapshot when one exists. The tries MUST NOT appear as separate runs. While a further try waits at the back, the page MUST show the stored status as scheduled and MUST NOT show it as finished or failed. A sign-in or token failure on any try MUST end the sequence at once and MUST NOT rejoin the queue. The worker stopping or crashing while a pass is running MUST follow FR-023. That reported `stalled` outcome MUST NOT be consumed as one of the 3 tries, MUST NOT change the stored status from `running`, and MUST NOT rejoin the queue. A further try already waiting at the back of the queue MUST still be taken after the scheduled collection process is back and MUST NOT be marked interrupted because of that stop. It MUST run only when that person is still allowed. If stored access cannot be used, the run fails with the sign-in or token reason, further tries stop, and later scheduled collections wait until the worker refresh token is stored again. The page MUST keep showing that waiting run as scheduled until the worker takes it, and as running only while that attempt has not yet recorded a terminal status. A collection the operator starts by hand MUST NOT receive these further tries.

- **FR-022**: In hosted sign-in the product MUST store one account scan status for each account seen under the daily fill's logged-in-within-the-last-30-days rule. The record MUST be created when that account is first recorded for later scanning, including when the access the scanner will use is stored. The default MUST be `never run`, with an empty last-run time, an empty result, and an empty comment. A later sign-in MUST NOT reset a record that has already left `never run`. The record MUST remain readable after the 30-day window closes. It MUST hold the status, the last scan time, the last result (success, failure, or empty), the result comment for that last run, and `suspensionReason` (`notAllowed` or empty). The comment MUST be Success when the last run succeeded, the failure detail when it failed, and empty when no scan has run. The status MUST be `never run`, `scheduled`, `running`, `finished`, or `suspended`, with the meanings in User Story 8. A further status MUST be stored only when it is a real state required to tell the truth. The page, and any other process that needs the current scan state, MUST read this record and MUST NOT infer running, finished, failed, or suspended from the clock, from a missing visit, or from the absence of a worker. When a hosted sign-in record exists and the status blob is absent, readers MUST report `never run` and MUST NOT write the blob on that read. The next completed sign-in, or the next fill before it decides who to queue, MUST create that `neverRun` blob when it is absent. That create MUST NOT reset a blob that already exists. Creating a queue entry MUST set `scheduled` and MUST clear `suspensionReason`, including a further try waiting at the back. A hand-started collection that sets `running` MUST clear `suspensionReason`. Before it decides who to queue, a live scheduled collection process MUST restore each account whose stored status is `scheduled` and that has no queue entry at all. An entry that exists but is not yet visible, including a further try waiting for its minimum delay, MUST count as a queue entry, and the status MUST stay `scheduled`. When no entry exists, an empty last result MUST set the status to `never run`, and any other last result MUST set the status to `finished`. The last scan time, last result, and result comment MUST stay as they were, and this restore MUST NOT add a failure comment. The same fill MUST then apply FR-001, which MAY queue that account. The worker taking that entry MUST set `running`. The worker finishing a completed try sequence MUST set `finished` with the result and comment. A refusal because the account is not allowed MUST set `suspended` and `suspensionReason` `notAllowed` without overwriting the last scan time, result, or result comment. When the worker credential cannot be used, that failure happens before the catalogue walk. - **FR-023**: While a hosted scan for an account is stored as `running` and that scan is still working, the process scanning that account MUST record a fresh liveness mark at least once every 60 seconds until that scan records `finished` or `suspended`. A lapse of the liveness mark MUST NOT by itself record `finished`, MUST NOT remove or rejoin the queue entry, and MUST NOT be treated as one of the three short failure reasons. A normal finish MUST still record `finished` with the real result and comment. Until a newer scan for that account is queued or started by hand, the pass that was scanning MAY record its real success or failure, including after callers have been told `stalled`. If that pass updates the liveness mark before a newer scan starts, callers MUST be told `running` again. A success MUST set `finished`, result success, and comment Success, and MUST replace the snapshot as any other success does. A failure MUST set `finished` with the real failure result and comment. Callers MUST then be told that finished status. Once a newer scan has set the stored status to `scheduled` or to a new `running`, that earlier pass MUST NOT change the stored status, the liveness mark, or the snapshot. A reported `stalled` account MUST NOT count as queued or in progress. A later fill MUST queue that account when FR-001's other rules allow, and that new queue entry MUST set the stored status to `scheduled`. The operator MUST be able to start a collection by hand while the account is reported `stalled`. That hand-started collection MUST set `running` and MUST update the liveness mark. The earlier queue entry MUST NOT rejoin. When a fill, another copy of the scheduled collection process, and a hand-started collection would otherwise start together, FR-008's single-winner rule applies: the first to set `scheduled` or a new `running` is the only new scan. A stop while the status is only `scheduled` MUST leave it `scheduled` until the entry is taken or removed by a real rule. The operator-facing app stopping MUST NOT by itself change a worker-owned stored status. In the lean local posture there is no scheduled scan status and this reported `stalled` status does not apply.


- **FR-025**: The Repositories page, and any other process that asks for the human-friendly text of the current scheduled scan, MUST receive the same sentences for the same reported status. The reported status token MUST still be available. When none exists, that sentence MUST be omitted. `{started at}`, `{finish time}`, and `{failed at}` are the times of that run. `{recorded count}` is how many repositories have been recorded on the current run. `{saved count}` is how many the saved snapshot contains, including zero. The human-friendly text MUST NOT say who started the run. The account scan status does not store that fact, and this feature MUST NOT add it for display.

  - `running`: "A collection is running. It started at {started at}. {recorded count} repositories recorded so far." The text MUST NOT say who started it.
  - `stalled`: "This collection has stopped reporting progress." The text MUST NOT say the run is running, MUST NOT use a failure reason, MUST NOT say the operator-facing app stopped, and MUST NOT say who started it.
  - `finished`, result success: "The last collection finished successfully at {finish time}. {saved count} repositories were saved." The stored comment Success MUST NOT be shown as the word Success. The text MUST NOT say who started it.

  - `suspended`, `suspensionReason` `notAllowed`: "Scheduled collection is paused because you are not allowed to use the product." The text MUST NOT describe a failed snapshot, MUST NOT add a failure reason, and MUST NOT say the scan is running.
  - `suspended`, result failure, `suspensionReason` empty: "Scheduled collection is paused until you refresh the access used for the overnight collection. The collection at {failed at} did not save a snapshot because of a sign-in or token problem." This is the case where no newer worker refresh token is already stored. When a newer worker refresh token is already stored, that failure is `finished` and MUST use the finished failure sentence, not this paused sentence.

  The schedule sentence is separate from the status sentence. Callers MUST receive at most one, in this order. When the next ask will queue the account, including while a queue entry is waiting and the scan has not started: "The next collection runs overnight." When the account is not allowed: "No scheduled collection will run because you are not allowed to use the product." Otherwise, when a stored-access wait is set: "No scheduled collection will run until you refresh the access used for the overnight collection." Otherwise, when the 30-day window is closed: "No scheduled collection will run until you sign in again." A stored-access failure MUST stay visible in the status sentence even when the schedule sentence says they are not allowed. In the lean local posture there is no scheduled scan status, and this catalogue does not apply. The existing explanation still says that nothing collects on a schedule, and that the snapshot is kept on this machine rather than promised on another machine.


### Key Entities

- **Scheduled collection process**: The part of the product that, in hosted sign-in, fills the scheduled scan queue at each occasion and processes that queue. It uses a worker refresh token stored during the same hosted sign-in, from a second GitHub authorisation on the existing GitHub App after the browser refresh token is already stored. One GitHub response is not split into both tokens. That worker token is not the refresh token in the auth cookie. The cookie keeps the refresh token from the first authorisation, and storing the worker token leaves that browser token usable and unchanged. The product keeps that worker token only when the browser refresh token still works afterwards. When it does not, the product discards that worker token and sends them through GitHub again on the existing GitHub App to restore the browser token. Sign-in is complete once that restored browser token works, and the worker token stays missing. Cancelling the second authorisation leaves the sign-in complete. Renewing only the worker token does not end the browser session. A completed sign-in that stores a worker refresh token replaces any previous one. A completed sign-in that does not store a worker refresh token leaves the scheduled collection with no worker refresh token it can renew. While that person stays signed in, storing a replacement worker refresh token ends a stored-access wait, does not move the 30-day window, does not replace the saved organisation list, and does not start a scan. The Repositories page asks them to choose a refresh of only that token as soon as it is missing, or as soon as an overnight scan has failed because it cannot be used. Choosing it sends them through GitHub authorisation again and stores only the worker token from that authorisation. It does not refresh the browser token. Cancelling, or a refresh that does not store a worker token, leaves them signed in and does not record a scan failure. The ask is on that page only. It is not the operator-facing app. The app does not have to be running for the queue to fill or for a scheduled collection to finish. The app stopping does not interrupt a scheduled pass and does not by itself miss a fill. If this process is not running at 05:00 UTC, it runs the same fill when it is back, at any time. That fill includes eligible people whose scan already succeeded earlier that day, when they are not already queued or in progress. Queued work is still taken at any time when the process runs, and that scan runs when the person is still allowed. If stored access cannot be used, the run fails with the sign-in or token reason, further tries stop, and later scheduled collections wait until the worker refresh token is stored again. If it stops or crashes while a pass is running, that pass is left stored as `running`. Once no liveness mark has been recorded for more than 5 minutes, callers are told `stalled`, not `running`. The stored status stays `running`. If it stops while work is only queued, that work is still taken when the process is back, at any time of day, and runs only when that person is still allowed. If stored access cannot be used, the run fails with the sign-in or token reason, further tries stop, and later scheduled collections wait until the worker refresh token is stored again. More than one copy still queues each eligible person once per occasion. This specification does not name its host, project, or wiring. It does not exist in the lean local posture.
- **Operator snapshot**: The single current collection for one operator, as the operator snapshot collection already defines it. A daily success and a hand-started success both write this same snapshot. It does not hold a history of older collections. It is readable only by that operator.
- **Account scan status**: The stored current state of scanning for one hosted account seen under the 30-day sign-in rule: `never run`, `scheduled`, `running`, `finished`, or `suspended`, plus the last scan time, last result, result comment, `suspensionReason` (`notAllowed` or empty), and the liveness mark used while the status is `running`. While that scan is still working, a fresh liveness mark is recorded at least once every 60 seconds until the scan records `finished` or `suspended`. It is not a history of past runs. The page and any other process read this record instead of guessing. When the stored status is `running` and no liveness mark has been recorded for more than 5 minutes, those readers are told `stalled`. `stalled` is not one of the stored statuses.
- **Collection run**: The operator-visible scan for one account, read from the account scan status. `scheduled` means a queue entry is waiting, including a further try at the back. `running` means the worker has taken it. `finished` means the worker has finished it with a real success or failure. `stalled` is the reported status when `running` has no liveness mark for more than 5 minutes. It is not stored. `suspended` means the worker took it and the scan cannot run again until the stated block is resolved. Waiting in the day's queue before the worker has taken the entry is shown as scheduled, not as running. A further try waiting at the back is shown as scheduled, not as failed, and the tries are not listed. A stop while the person is only waiting, including during that further-try wait, leaves the status `scheduled`. A stop or crash while a pass is running leaves the stored status `running`. Once no liveness mark has been recorded for more than 5 minutes, the operator-visible status is `stalled`, and that pass does not rejoin the queue. This feature adds whether the current run was started by the operator or by the overnight collection, and the FR-025 statement of whether a collection will run. Those words do not name 05:00 UTC. A daily run that is being tried again after a rate limit or an unexpected error stays one run until it succeeds or fails. While it waits at the back of the queue for the applicable minimum wall-clock wait, the status is `scheduled`. That waiting further try is still taken after the scheduled collection process is back, and runs when that person is still allowed and the minimum wait has elapsed. If stored access cannot be used, the run fails with the sign-in or token reason, further tries stop, and later scheduled collections wait until the worker refresh token is stored again. Timing, counts, and the short reason stay as the operator snapshot collection already defines them. The recorded failure reason is shown with the finish time of the latest successful snapshot when one exists.
- **Scheduled occasion (queue fill)**: The moment the product fills the scheduled scan queue for a planning cycle. The initial delivery asks once per UTC calendar day, nominally at 05:00 UTC. A fill at any time queues people whose latest completed hosted sign-in is no older than 30 days at that fill, who are currently allowed, who are not waiting because stored access could not be used, and who are not already queued or in progress. An earlier success the same day does not exclude them. If the process is not running at 05:00 UTC, it runs that fill when it is back. Each queued request runs one at a time when the process is running. Two copies at the same fill do not queue the same person twice while they are already queued or in progress. The operator-facing app does not have to be running, and it does not perform the fill. It is not a scan of everyone who is allowed. It is not a separate snapshot. It does not exist in the lean local posture. A missed or skipped fill is not stored as its own record. The operator does not see the queue.
- **Sign-in window**: The 30 days after a person's latest completed hosted sign-in. Only a completed sign-in moves it. A collection does not. That same completed sign-in saves the organisation logins used later to decide organisation allowance. The daily occasion does not replace those logins.

The auth cookie keeps the first authorisation's refresh token, so a scheduled scan renews only the worker token and does not sign the operator out of the browser. The product keeps that worker token only when the browser refresh token still works afterwards. When it does not, the product discards that worker token and restores the browser token through GitHub again. Sign-in is complete once the restored browser token works, and the worker token stays missing. Cancelling that second authorisation leaves the sign-in complete.
- A hand-started collection in hosted sign-in uses the signed-in session and does not use the worker token. A missing or unusable worker token does not stop that collection. An overnight scan still uses only the worker token.
- Storing a replacement worker refresh token while the operator stays signed in, by a second GitHub authorisation, without signing out and without completing hosted sign-in again. That authorisation stores only the worker token. It does not refresh the browser token. That refresh ends a stored-access wait, does not move the 30-day window, does not replace the saved organisation list, and does not start a scan. The Repositories page asks for that refresh as soon as the signed-in operator's worker token is missing, or as soon as an overnight scan has failed because that token cannot be used. They choose it. Cancelling or a failed refresh leaves them signed in.

### Out of scope

- A second scanner, a second snapshot, or a different set of repository facts.
- Any schedule in the lean local posture, and any scheduled collection process in that posture.
- Naming the host, project, or wiring of the scheduled collection process.
- Requiring the operator-facing app to be running for the daily collection to be queued or to finish.
- A control or settings page for the operator to change the fill time, how often the queue is filled, or the 30 days. This delivery keeps asking once per UTC day at 05:00 UTC. The fill rules are the 30-day sign-in, permission, stored access, and not already queued or in progress. A later feature may ask more often, including every 10 minutes, or offer per-operator schedules, without changing those fill rules or the queue-processing rules in this specification.
- A stored history of daily occasions, past runs, or the individual tries inside one daily run.
- Guessing the current scan state from the clock, from a missing page visit, or from the absence of a worker.
- Changing who the daily fill queues, or how often this delivery asks for a fill.
- A retry control, or any other way to collect again by hand beyond the start control the operator snapshot collection already provides.
- Automatic further tries for a collection the operator started by hand.
- Community-standard gaps, FUNDING status, and any later facts the operator snapshot collection left for other features.
- Writing or copying repository files to GitHub.
- Sharing one refresh token between the scheduled collection and the auth cookie, or renewing that cookie from a refresh token the worker rotated.
- A new sign-in mode for the worker credential. Hosted sign-in remains the only hosted sign-in.
- Forcing the operator to sign out and complete hosted sign-in again as the only way to store a replacement worker refresh token while the browser session is still valid.
- A prompt on every page to refresh the worker token, or a separate settings area for that refresh. The ask is on the Repositories page.

## Assumptions

- The daily collection belongs only to hosted sign-in and is performed by a scheduled collection process that is not the operator-facing app. The app does not have to be running for that collection to be queued or to finish. This specification does not name the host, project, or wiring of that process. The lean local posture, including a personal deployment that stays in that posture, has no scheduled collection process and does not get a schedule. That is the split this request asked for between the shared sign-in posture and use on the operator's own machine.
- The daily set is every person who has completed a hosted sign-in at least once in the last 30 days and who is currently allowed to use the product, minus anyone waiting after a daily collection failed because stored access could not be used. There is no separate choice to turn the schedule on or off in this feature.
- Current permission uses the existing hosted admission rules at fill time for each scheduled occasion, and again when a queued entry is about to run and when the Repositories page states the next occasion. At fill, when admission is on, a person is allowed when their user login is listed or an organisation login saved from their last completed sign-in is on the organisation list as it stands at that fill instant. At dequeue and at page read, the same rule uses those allow lists as they stand at that current moment, still compared only with organisation logins saved from the last completed sign-in. The product does not ask GitHub again only to check membership, so leaving or joining a GitHub organisation takes effect at the next completed sign-in. When admission is off, those lists do not refuse anyone. The lists are not scanned in full: a listed person who has never completed sign-in is not scanned. A person who was allowed and is then refused is not queued at the next fill, even inside the 30 days. Removing an organisation from the allow list stops queueing only for people who have no remaining way to be allowed from their user login or their saved organisation logins. Allowing someone again does not require a new sign-in while the existing window is still open and they are not waiting after invalid stored access.
- The human-friendly text says the next collection runs overnight only when that occasion will queue a collection for that operator. It uses that same sentence before today's 05:00 UTC ask, while they are still waiting in today's queue, and after today's ask when the following ask would include them. It does not name 05:00 UTC, today, or the following day. A successful scan does not make a sooner fill refuse them. The operator-facing app being down does not, by itself, cancel a fill. Eligibility means a completed sign-in no older than 30 days at that occasion, currently allowed, and not waiting after invalid stored access. A credential failure, a closed window, or a loss of permission is stated as no scheduled collection, not as a claim that the next collection runs overnight. The page uses one schedule sentence, in this order: they are not allowed; otherwise the stored-access wait until they refresh the access used for the overnight collection; otherwise the closed 30-day window until they sign in again. When a stored-access wait is set, that failed run stays visible even if the schedule sentence says they are not allowed.
- "Signed in" in this feature means a hosted sign-in that completed. Storing the browser refresh token completes it even when the worker refresh token is not stored. A sign-in that does not complete does not open or restart the 30 days and does not lift a wait after invalid stored access. A completed sign-in lifts that wait only when it stores the worker refresh token. A worker-token refresh while they stay signed in also lifts that wait when it stores the worker refresh token, and does not move the 30-day window or the saved organisation list, and does not start a scan. Until the worker refresh token is stored again, the next overnight scan fails with the sign-in or token reason when they are not already in that wait.
- The 30 days are measured at fill time from the latest completed sign-in, using the instant that fill actually runs. For this delivery's planned ask that instant is 05:00 UTC. A fill at another time uses that later instant. A sign-in exactly 30 days earlier is still inside the window. A sign-in older than 30 days is outside it. A successful collection does not move the window. Only a completed sign-in does.
- The wait after invalid stored access applies only when a daily collection fails with the existing sign-in or token reason. That failure is not tried again that occasion. The failing run still happens and stays visible, including the finish time of the latest successful snapshot when one exists. The page does not say that the next collection runs overnight. Later occasions do not start another run until the worker refresh token is stored again, and only when the person is also currently allowed and the 30-day window is still open. A completed sign-in that does not store that token restarts the 30-day window and does not lift the wait. A worker-token refresh while they stay signed in is a second GitHub authorisation that stores only that token, lifts the wait, does not refresh the browser token, does not move the 30-day window, does not replace the saved organisation list, and does not start a scan. A queued scan that has not been taken uses the worker token stored when it is taken. A scan already running keeps the token it started with. When GitHub issues a replacement for that token, the scan does not write it over a newer worker token already stored. The newer token stays stored. The scan may store a replacement only while the token it started with is still the stored worker token. If that running scan then fails because of that older token, and a newer worker token is already stored, the failure stays visible as `finished` and the wait is not set. When that refresh lifts a wait whose status is `suspended` because stored access could not be used, the status becomes `finished` with the same failure result and comment. A rate limit, an unexpected error, a reported `stalled` scan, a missed day, or a run already in progress does not start that wait.
- "Up to 3 times" means up to 3 further tries after the first attempt, so at most 4 attempts in that run. Each further try goes to the back of the queue. Before it may start, the product waits at least the applicable minimum wall-clock period: for a rate-limit failure, at least the GitHub-indicated retry period when the product already has one from that failure, otherwise at least 2 minutes; for an unexpected-error failure, staggered minimum waits measured from that failed attempt: at least 3 minutes before the first further try, at least 6 minutes before the second further try, and at least 12 minutes before the third further try. Other accounts already queued ahead run first. When no other account is ahead, the further try still must not start until that minimum has elapsed; queue position alone is not enough. The wait is not held in front of those other accounts, and it is not a wait until the next day. The operator cannot see the queue, their place in it, or a list of tries. While a further try waits, the page shows the stored status as scheduled. Each further try is a fresh pass of the same collection. Only a pass that succeeds replaces the snapshot. A sign-in or token failure on any attempt ends the sequence immediately and does not rejoin the queue.
- Completing sign-in does not fill the queue by itself. A later fill includes them when they are eligible and not already queued or in progress, including after a successful scan. A successful scan is not repeated solely because they sign in again.
- For the initial delivery default, the named fill clock time is 05:00 UTC for every operator. It is not 05:00 in the operator's local zone. This delivery asks once each UTC day at 05:00 UTC. That ask is not a time window and not a cap. A later feature may ask more often, including every 10 minutes. This feature does not add a control for that. Queue processing is not tied to that hour.
- Eligible people are placed on one queue at each scheduled fill. Under the daily default that is nominally 05:00 UTC. One scheduled collection runs at a time. A run that starts at any later time is still that occasion's queued work, processed when the queue reaches that person. If a collection for that operator is already in progress, or they are already on the previous occasion's queue, the new fill does not add another entry. When more than one copy of the scheduled collection process is running, each eligible person is still queued once for that fill.
- If the scheduled collection process is running at 05:00:00 UTC, the fill runs then. If it is not, the same fill runs when the process is back, at any time. Each fill queues eligible people who are not already queued or in progress, including after a successful scan. A queue that was already filled is still taken after the scheduled collection process returns, including a further try waiting at the back. The scan runs when that person is still allowed. If they are not allowed, the entry is removed, the stored status is suspended with `suspensionReason` `notAllowed`, and the last scan time, result, and result comment are not overwritten because no scan ran, and the next queued person is taken. If stored access cannot be used, the run fails with the sign-in or token reason, further tries stop, and later scheduled collections wait until the worker refresh token is stored again. A pass that was running when the worker stopped or crashed is left stored as `running`. Once no liveness mark has been recorded for more than 5 minutes, callers are told `stalled`, not `running`. The earlier queue entry does not rejoin. A reported `stalled` account does not count as in progress. A later fill queues that account when the other eligibility rules allow, and that new queue entry sets the stored status to `scheduled`. The operator may start a collection by hand while the account is reported `stalled`. That hand-started collection sets `running` and updates the liveness mark. The earlier queue entry does not rejoin. A further try that was only waiting stays shown as scheduled until the worker takes it, it finishes, or loss of permission sets suspended.
- The daily collection reads the same personal catalogue as a hand-started collection. In hosted sign-in a hand-started collection uses the signed-in session and does not use the worker token. A missing or unusable worker token does not stop that collection. An overnight scan uses only the worker token. Each completed hosted sign-in stores a refresh token in the auth cookie from the first GitHub authorisation on the existing GitHub App. When that sign-in also stores a worker refresh token, it comes from a second GitHub authorisation in that same sign-in, it replaces any previous worker refresh token, and the browser refresh token stays usable and unchanged. The product keeps that worker token only when the browser refresh token still works afterwards. When it does not, the product discards that worker token, restores the browser token through GitHub again, and leaves the worker token missing until a later authorisation stores one without leaving the browser token unusable. Sign-in is complete once the restored browser token works. One GitHub response is not split into both tokens. When it does not, including when the operator cancels that second authorisation, the sign-in is still complete and the scheduled collection has no worker refresh token it can renew. The next overnight scan then fails with the sign-in or token reason until the worker refresh token is stored again. The overnight scan may renew only that worker token. Obtaining fresh access for the scan does not ask them to sign in again and does not end a browser session that is still valid. If the worker credential cannot be used, the existing sign-in or token reason applies. That failure is not repaired by spending the browser refresh token.
- What a snapshot contains, which short reasons the operator sees, and the rule that only the latest success is kept stay as defined for the operator snapshot collection. This feature changes when a collection can start. The account scan status does not record who started the run, and the page does not say who started it.
- The overnight start is there so a collection that grows slower over time does not have to be watched. The run may still be in progress after 05:00 UTC. The operator is not required to stay on the page until it finishes.
- Operator-facing text uses UK English.
- The account scan status is written only from events that happened: a record created, a queue entry created, the worker taking it, the worker finishing it, a rule that suspends it, or the worker ending after it had taken the entry. The page does not invent a status to fill a gap.
- The Repositories page remains the only place the operator reads collection status and starts a collection by hand.
